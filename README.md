# LzmaSharp

Управляемая реализация на C# для семейства алгоритмов LZMA / LZMA2 и обработки
контейнера 7z. Цель проекта — собственное читаемое управляемое ядро без скрытой
магии работы с памятью.

## Установка

```bash
dotnet add package Ti-Soft.LzmaSharp
```

Пакет публикуется по тегам `core/X.Y.Z`; версия выводится из тега (MinVer). `Lzma.Core` собирается
под `net8.0`, поэтому пригоден для приложений на .NET 8 и новее; UI и тесты — `net10.0`.

## Статус

Ядро опубликовано как NuGet-пакет **`Ti-Soft.LzmaSharp`** (актуальную версию смотрите на
[nuget.org](https://www.nuget.org/packages/Ti-Soft.LzmaSharp); на момент последней сверки —
1.2.0). Сборка и тесты идут в CI на трёх ОС (ubuntu, windows, macos), включая интероп-проверки
с настоящим консольным 7-Zip (`7zz`), который workflow устанавливает сам.

Работы по безопасности (реестр — [`docs/plans/SECURITY_REMEDIATION_PLAN.md`](docs/plans/SECURITY_REMEDIATION_PLAN.md)):

- **закрыто и опубликовано** (1.1.0 / 1.2.0): транзакционное создание архива и многотомных
  наборов (SEC-002), транзакционное извлечение с откатом и восстановлением прежних байт и
  атрибутов (SEC-001), отклонение извлечения при ссылках и junction в цепочке пути назначения
  (SEC-003 — частично);
- **в работе** (фаза C): бюджеты памяти и вывода (SEC-004, RES-001/002/003). Аллокации по
  счётчикам недоверенного заголовка 7z уже ограничены объёмом, который вход способен описать
  (RES-001); формальная политика предела in-memory распаковки утверждена и реализуется.

Что именно гарантируется и что **не** гарантируется (окно «проверка → открытие», mount point,
нормализация Unicode, пределы памяти) — в [`docs/SDL.md`](docs/SDL.md). Текущая рабочая точка
и ближайшие шаги — в [`docs/plans/CURRENT_WORK_STATE.md`](docs/plans/CURRENT_WORK_STATE.md).

Карта этапов развития ядра — в [`docs/ROADMAP.md`](docs/ROADMAP.md), статус writer/encoder —
в [`docs/STAGE2_WRITER_STATUS.md`](docs/STAGE2_WRITER_STATUS.md). Завершены этапы 1 (decoder-path
7z), 1.5 (AES/7zAES), 1.6 (экспериментальный GOST, чтение и запись); этап 2 (запись данных и
архивов, собственный LZMA/LZMA2-энкодер) продолжается.

## Что уже работает

### Чтение и распаковка 7z

Decoder-path поддерживает методы и фильтры: `Copy`, `LZMA`, `LZMA2`, `Delta`, `Swap2`,
`Swap4`, BCJ-фильтры (`x86`, `ARM`, `ARMT`, `ARM64`, `PPC`, `SPARC`, `IA64`), `BCJ2`,
`BZip2`, `PPMd`, `Deflate`, `Deflate64`. Также поддержаны AES-сценарии чтения и
экспериментальный GOST decoder-path.

> GOST-расширение LzmaSharp является внутренним экспериментальным форматом
> с поддержкой чтения и записи. Оно не совместимо со стандартным 7-Zip и
> использует закрытые идентификаторы методов проекта. Текущая версия формата
> не содержит криптографического тега аутентификации, охватывающего шифротекст
> и существенные параметры формата. CRC позволяет обнаруживать случайные
> повреждения, но не является криптографическим MAC и не обеспечивает защиту
> от преднамеренной модификации. Формат не рекомендуется для производственного
> применения или защищённого долговременного хранения.

Контур распаковки валидирует пути вывода до записи на диск: отклоняются абсолютные и
небезопасные пути, выход за пределы целевой директории, зарезервированные имена Windows,
коллизии и конфликты структуры. Если компонент пути назначения является символической ссылкой
или junction, извлечение **отклоняется до первой записи** (общий флаг reparse-point, единый
механизм на Windows, Linux и macOS; при нечитаемых атрибутах компонента — отказ в пользу
сохранности данных). Границы честности: ссылка, созданная после проверки пути, не обнаруживается
(окно «проверка → открытие» без P/Invoke не закрывается), mount point общим флагом не
обнаруживается, эквивалентность имён в разных формах Unicode (NFC/NFD) платформенно-зависима.
Подробности — в [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) и [`docs/SDL.md`](docs/SDL.md).

Счётчики в заголовке 7z (число папок, кодеров, потоков, файлов, размеров) ограничиваются объёмом,
который вход способен описать, поэтому запрос гигантских аллокаций недоверенным заголовком
отклоняется контролируемым результатом вместо исчерпания памяти. Формальная политика предела
распакованного объёма — в работе (см. «Статус»).

Извлечение **ZIP** выполняется через временный файл рядом с назначением: результат публикуется
только после успешной проверки, а при отказе операция откатывается целиком — прежние байты
перезаписываемых файлов восстанавливаются из backup, созданного переименованием. Перед первой
записью выполняются две проверки: свободное место тома назначения (при нехватке —
`ZipExtractResult.InsufficientSpace`, оценка приближённая, измерение best-effort) и длина путей
с учётом имени временного файла (при превышении принятого лимита — `ZipExtractResult.PathTooLong`);
в обоих случаях существующие файлы не затрагиваются. Извлечение **7z** использует тот же механизм
стадии и отката: файлы folder-а публикуются только после проверки результата декодирования,
при отказе прежние байты и атрибуты файлов восстанавливаются из backup. Перед первой записью данных для 7z
проверяются свободное место (сумма распакованных размеров выбранных элементов, best-effort)
и длина путей с учётом суффикса стадии — при превышении возвращаются аддитивные значения
`SevenZipArchiveDecodeResult.InsufficientSpace`/`PathTooLong`; известные ограничения
(root назначения и промежуточные компоненты) — см. `docs/SDL.md`.

### Чтение и запись ZIP

- Методы: **Store** и **Deflate** (собственный управляемый Deflate), на чтение также Deflate64.
- **ZIP64** — архивы больше 4 ГиБ и с числом записей больше 65535 (потоковый путь).
- **Потоковость** — потоковое чтение каталога и создание ZIP; извлечение по пути без загрузки
  всего архива в память. In-memory путь (`ZipReader`/`ZipWriter`) ограничен ~2 ГиБ.
- **WinZip-AES (AES-256)** — чтение и запись зашифрованных членов, совместимо с 7-Zip/WinZip.
  Legacy ZipCrypto не поддержан. Зашифрованный член при извлечении буферизуется целиком,
  `CompressedSize > int.MaxValue` отклоняется как неподдерживаемый.
- Извлечение ZIP использует тот же механизм стадии и отката, что и 7z (см. ниже).

### Запись 7z (этап 2)

Базовый writer через `SevenZipArchiveWriter.BuildArchive(...)` умеет писать пустой архив,
пустые файлы и директории, непустые файлы (методы `Copy`, **`LZMA2`**, **`PPMd`** или
**`Auto`** — выбор кодека по содержимому — через `SevenZipWriterCompressionMethod`),
mixed-сценарии, безопасные вложенные `/`-paths, а также `FilesInfo.WinAttrib` и `FilesInfo.MTime`.
Архивы `LZMA2` и `PPMd` распаковываются настоящим **7-Zip** побайтово.

> Интероп-проверки выполняются и в CI на трёх ОС: workflow ставит официальный консольный
> 7-Zip (`7zz`) на ubuntu и macos, на Windows используется предустановленный 7-Zip. Тесты
> требуют исполняемый файл явно и падают с внятным сообщением, если он не найден (тихий
> пропуск устранён). Локально путь можно задать переменной окружения `SEVENZIP_PATH`.

Энкодер даёт **реальное сжатие**: match finder питает `LzmaAloneEncoder.Encode(...)` (`.lzma`)
и LZMA2-writer. Сжатые `.lzma` и `.7z` (LZMA2) распаковываются настоящими **7-Zip** и **`xz`**
побайтово. Дальнейшие шаги — rep-дистанции, lazy parsing и производительность
(см. [`docs/STAGE2_WRITER_STATUS.md`](docs/STAGE2_WRITER_STATUS.md) и
[`docs/ENCODER_MVP_PLAN.md`](docs/ENCODER_MVP_PLAN.md)).

**Запись в поток** (`SevenZipArchiveWriter.Build*ArchiveToStream(...)`) последовательно
записывает архив в доступный для записи и позиционирования `Stream`. Это не является
общей гарантией ограниченного потребления памяти: модель памяти зависит от выбранного
метода. В LZMA2 файлы, превышающие внутренний размер блока, кодируются блоками
непосредственно в выходной поток, а меньшие файлы могут буферизоваться параллельными
группами. PPMd имеет отдельный потоковый путь для файлов выше заданного порога.
`Copy`, `Auto` и `BCJ2` используют пофайловую буферизацию и имеют собственные
ограничения размера.

Прикладной слой (UI) — в [`docs/STAGE4_UI_STATUS.md`](docs/STAGE4_UI_STATUS.md).

## Принципы разработки

- Маленькие проверяемые шаги; следующий шаг — после того, как предыдущий работает.
- Сначала корректность и тесты, потом оптимизация.
- Понятный и честный C# без скрытой магии.
- Комментарии, XML-документация и заголовки коммитов — на русском языке.
- Документация в `docs/` — основной источник правды о состоянии проекта.

## Сборка и тесты

Версия SDK закреплена в `global.json`; требуется .NET SDK 10 (сборка `Lzma.Core` — `net8.0`).
Полный граф NuGet-зависимостей зафиксирован в `packages.lock.json` каждого проекта: в CI
восстановление идёт в locked-режиме, поэтому расхождение состава даёт ошибку `NU1004`/`NU1403`,
а не тихую подмену версий; локально обычный `restore` обновляет lock-файл сам.

```bash
dotnet build -c Release
dotnet test tests/Lzma.Core.Tests -c Release
dotnet test tests/Lzma.Ui.Tests -c Release
```

CI (`.github/workflows/ci.yml`) на каждом пуше ветки: ubuntu, windows и macos — сборка Release,
гейт аудита уязвимостей зависимостей (`dotnet list package --vulnerable --include-transitive`)
и полный прогон тестов, включая интероп с настоящим 7-Zip (`7zz` устанавливается workflow;
локально путь можно задать переменной `SEVENZIP_PATH`). Публикация пакета
(`.github/workflows/publish-core.yml`) выполняется по тегу `core/*` через NuGet trusted publishing
(OIDC) и включает **блокирующий** шаг SBOM (CycloneDX, версия тулзы закреплена): релиз без
`bom.json` не публикуется.

## Внешние зависимости

У `Lzma.Core` **нет внешних codec-зависимостей** — все методы декодируются и кодируются
собственными управляемыми реализациями:

- `Deflate`, `Deflate64` — `DeflateDecoder` (RFC 1951 + режим Deflate64), `DeflateEncoder`;
- ZIP-контейнер — `ZipReader` / `ZipWriter` (Store + Deflate);
- `BZip2` — `BZip2Decoder` / `BZip2Encoder`;
- `PPMd` — `Ppmd7Decoder` / `Ppmd7Encoder` (PPMd var.H / 7z; поток энкодера бит-в-бит
  совпадает с настоящим 7-Zip).

`SharpZipLib` и `SharpCompress` полностью удалены из production. `SharpZipLib` оставлен только
в тест-проекте как эталон для round-trip сверки BZip2. Сторонние компоненты и их лицензии
перечислены в [`THIRD_PARTY_NOTICES.md`](THIRD_PARTY_NOTICES.md).

## Цепочка поставки

- эталонные исходники LZMA SDK зафиксированы в `vendor/lzma-sdk/` с версией, датой, источником
  и SHA-256 манифестом;
- полный граф зависимостей закреплён lock-файлами, в CI восстановление в locked-режиме;
- состав зависимостей проверяется в CI гейтом по опубликованным advisory (блокирующим);
- к каждому релизу прикладывается SBOM (CycloneDX) — шаг публикации блокирующий;
- подробности и границы мер — в [`docs/SDL.md`](docs/SDL.md) §4 и
  [`docs/PROVENANCE.md`](docs/PROVENANCE.md).
