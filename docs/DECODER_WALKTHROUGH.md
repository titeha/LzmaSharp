# Пошаговый разбор декодера LZMA / LZMA2

## Назначение документа

Этот документ показывает, как текущий низкоуровневый декодер проходит входной поток LZMA2 и где внутри этого процесса вызывается LZMA-декодер.

`DECODER_OVERVIEW.md` даёт общую карту компонентов. Этот файл дополняет её пошаговым walkthrough: что происходит с входными байтами, как читаются чанки, где уменьшаются размеры и какие инварианты важно не сломать при отладке или оптимизации.

Документ относится к низкоуровневой части LZMA / LZMA2 и не описывает весь контейнер 7z.

## Общая идея

LZMA2 — это не сам алгоритм сжатия в чистом виде, а контейнер из чанков.

Каждый чанк говорит декодеру:

- это конец потока;
- это несжатые данные, которые нужно просто скопировать;
- это LZMA-сжатые данные;
- нужно ли сбросить словарь;
- нужно ли сбросить состояние LZMA;
- нужно ли прочитать новые LZMA-свойства.

Внутри LZMA2-сжатого чанка работает обычный LZMA-декодер.

## Главные состояния

Упрощённо декодер всё время находится в одном из режимов:

1. ждёт управляющий байт `Control`;
2. читает размер распакованных данных;
3. читает размер упакованных данных;
4. читает свойства LZMA, если они нужны;
5. обрабатывает данные текущего чанка;
6. завершает поток.

Если вход заканчивается посередине одного из шагов, декодер не должен считать это повреждением. Он должен сохранить промежуточное состояние и вернуть результат вида `NeedMoreInput`.

## Шаг 1: чтение `Control`

Каждый LZMA2-чанк начинается с одного управляющего байта.

Основные случаи:

- `0x00` — конец LZMA2-потока;
- значения для copy/uncompressed chunk — дальше идут несжатые данные;
- значения `>= 0x80` — дальше идёт LZMA-сжатый chunk.

Именно `Control` определяет, какие следующие поля нужно читать и какие сбросы состояния выполнить.

## Шаг 2: конец потока

Если `Control == 0x00`, поток завершён.

После этого декодер не должен пытаться читать:

- `UnpackSize`;
- `PackSize`;
- свойства LZMA;
- данные чанка.

Это важный инвариант для streaming-сценариев. Если outSize известен заранее, ошибка в обработке end marker может долго не проявляться, потому что вызывающий код может завершить декодирование по ожидаемому размеру. Но для корректного потокового поведения end marker всё равно должен обрабатываться явно.

## Шаг 3: copy / uncompressed chunk

Copy-чанк содержит данные, которые не нужно пропускать через LZMA.

Для такого чанка декодер:

1. читает размер распакованных данных;
2. копирует доступную часть входа в словарь;
3. уменьшает `UnpackSize`;
4. двигает позиции входа и выхода;
5. если вход закончился раньше, возвращает `NeedMoreInput`;
6. если `UnpackSize` стал равен нулю, переходит к следующему `Control`.

Важный момент: copy-чанк всё равно пишет в тот же словарь, что и LZMA-чанки. Эти данные становятся историей для последующих match-ссылок.

## Шаг 4: LZMA chunk

Для LZMA-сжатого чанка декодер читает больше служебных данных.

Обычно нужны:

- `UnpackSize` — сколько байт должен выдать этот чанк;
- `PackSize` — сколько packed-байт принадлежит этому чанку;
- LZMA properties, если `Control` говорит, что они обновляются.

После чтения заголовка LZMA2 передаёт payload во вложенный LZMA-декодер.

## Шаг 5: сброс словаря и состояния

`Control` у LZMA-чанка кодирует не только тип чанка, но и сбросы.

Возможны разные варианты:

- сбросить словарь;
- сбросить LZMA-состояние;
- прочитать новые свойства LZMA;
- продолжить с текущим словарём и текущими свойствами.

Словарь и состояние — разные вещи.

Словарь хранит уже выданные байты и нужен для match-копирования назад.

LZMA-состояние включает probability-модель, range coder и внутренние состояния декодера.

Нельзя автоматически считать, что сброс одного всегда означает сброс другого.

## Шаг 6: чтение LZMA properties

Когда `Control` требует новые свойства, декодер читает один байт LZMA properties.

Из него восстанавливаются:

- `lc`;
- `lp`;
- `pb`.

Если свойства невозможны, декодер должен вернуть `InvalidData`.

Если свойств не хватает во входе, это `NeedMoreInput`, а не `InvalidData`.

## Шаг 7: передача payload во вложенный LZMA-декодер

Когда заголовок LZMA2-чанка полностью прочитан, декодер запускает LZMA-декодер.

При этом он передаёт два ограничения:

- нельзя прочитать больше `PackSize` packed-байт;
- нельзя выдать больше `UnpackSize` распакованных байт.

LZMA-декодер может завершиться по-разному:

- выдал нужный объём данных;
- съел весь доступный input и попросил ещё;
- обнаружил повреждение данных;
- попал в сценарий, который текущая реализация не поддерживает.

Результат LZMA-декодера должен быть аккуратно преобразован в результат внешнего LZMA2-декодера.

## Шаг 8: уменьшение `PackSize`

`PackSize` уменьшается только тогда, когда декодер реально потребил packed-байты текущего LZMA-чанка.

Нельзя уменьшать `PackSize` заранее только потому, что байты доступны во входном буфере.

Типовой порядок:

1. определить, сколько packed-байт можно передать LZMA-декодеру;
2. вызвать LZMA-декодер;
3. получить количество реально потреблённых байт;
4. уменьшить `PackSize` на это число;
5. уменьшить `UnpackSize` на число реально выданных байт.

Если `PackSize` остаётся больше нуля, текущий LZMA-чанк ещё не завершён.

## Шаг 9: уменьшение `UnpackSize`

`UnpackSize` показывает, сколько байт ещё должен выдать текущий чанк.

Для copy-чанка он уменьшается при прямом копировании.

Для LZMA-чанка он уменьшается по фактическому числу байт, записанных вложенным LZMA-декодером.

Когда `UnpackSize == 0`, текущий чанк завершён. Декодер возвращается к чтению следующего `Control`.

## Шаг 10: роль `TempBuf`

`TempBuf` нужен для неполных заголовков.

Например, вызывающий код может дать вход так, что в буфере есть:

- только `Control`;
- `Control` и один байт размера;
- часть `PackSize`;
- заголовок без properties.

В таких случаях декодер не должен терять уже прочитанные байты. Он складывает их в `TempBuf`, запоминает `TempBufSize` и продолжает с этого места при следующем вызове.

Это особенно важно для incremental / streaming API.

## Шаг 11: первый байт LZMA payload

В LZMA payload есть важная проверка инициализации range coder-а.

Если первый байт там не тот, который ожидает LZMA-декодер, поток почти наверняка повреждён или смещение чтения посчитано неправильно.

Такие ошибки обычно проявляются как `InvalidData`.

При отладке проблем вокруг этого места полезно проверять:

- где начинается LZMA payload;
- не съеден ли лишний байт заголовка;
- не забыли ли уменьшить `PackSize`;
- не перепутаны ли границы properties и данных.

## Шаг 12: завершение чанка

Чанк считается завершённым только когда выполнены условия его типа.

Для copy-чанка:

- все `UnpackSize` байт скопированы.

Для LZMA-чанка:

- выдано нужное количество unpacked-байт;
- состояние LZMA-декодера согласовано с текущим chunk-контрактом;
- следующий вызов может читать новый `Control`.

Если чанк завершён, а во входе ещё есть байты, эти байты относятся уже к следующему LZMA2-чанку или к внешнему контейнеру, в зависимости от уровня вызова.

## Как читать трассировку

При отладке полезно логировать события в таком порядке:

```text
control
chunk type
need init dictionary
need init state
unpack size
pack size
props, если есть
data start offset
data consumed
bytes written
remaining pack size
remaining unpack size
next state
```

Для LZMA payload отдельно полезны:

```text
payload offset
payload first bytes
dicPos
processedPos
checkDicSize
range
code
lc/lp/pb
result
src consumed
dest written
```

## Типовой сценарий copy-чанка

```text
input:
  control = copy
  unpack size = N
  N raw bytes

decoder:
  читает control
  читает unpack size
  копирует raw bytes в словарь
  уменьшает unpack size до 0
  переходит к следующему control
```

Ожидаемый результат:

- `Ok`, если входа достаточно;
- `NeedMoreInput`, если raw bytes пришли не полностью;
- `InvalidData`, если нарушен формат заголовка.

## Типовой сценарий LZMA-чанка

```text
input:
  control = lzma
  unpack size = U
  pack size = P
  props, если требуются
  P байт LZMA payload

decoder:
  читает control
  читает unpack size
  читает pack size
  читает props при необходимости
  запускает LZMA-декодер
  уменьшает pack size на consumed
  уменьшает unpack size на written
  завершает chunk при unpack size == 0
```

Ожидаемый результат:

- `Ok`, если chunk полностью обработан;
- `NeedMoreInput`, если не хватило packed data;
- `InvalidData`, если payload повреждён;
- `NotSupported`, если вложенный LZMA-декодер упёрся в неподдержанный режим.

## Частые ошибки при изменении кода

### Слишком рано уменьшили `PackSize`

Если уменьшить `PackSize` до фактического потребления байтов, следующий вызов может начать читать новый chunk с неправильного смещения.

### Забыли сохранить неполный заголовок

Если не сохранить байты заголовка в `TempBuf`, incremental-декодер будет ломаться на входе, нарезанном маленькими частями.

### Перепутали сброс словаря и сброс состояния

Сброс словаря и сброс probability/state — разные операции. Их нельзя бездумно объединять.

### Неправильно обработали `Control == 0x00`

End marker должен завершать поток, а не запускать чтение следующего поля заголовка.

### Не различили `NeedMoreInput` и `InvalidData`

Недостаток входа — не всегда повреждение. Для streaming API это нормальное состояние.

## Что проверять после изменений

После изменения LZMA / LZMA2-декодера нужно прогонять:

```bash
dotnet test tests/Lzma.Core.Tests/Lzma.Core.Tests.csproj --filter FullyQualifiedName~Lzma
```

Если изменение влияет на 7z pipeline, дополнительно прогонять:

```bash
dotnet test tests/Lzma.Core.Tests/Lzma.Core.Tests.csproj --filter FullyQualifiedName~SevenZip
```

Перед крупным коммитом:

```bash
dotnet test
```
