# План по производительности: что оптимизируем и как

## 1) Сначала измеряем

Добавляем `BenchmarkDotNet` и базовый набор бенчмарков:

- Decode LZMA2: 1 MiB / 64 MiB / 1 GiB (стриминг)
- Encode LZMA2: те же размеры
- Собственные кодеки (encode + decode): `Deflate`, `BZip2`, `PPMd` — теперь все реализованы
  и проверены реальными инструментами, поэтому их горячие пути тоже под замер;
- ZIP-контейнер (`ZipWriter`/`ZipReader`) на наборах из многих файлов;
- «Плохие» и «хорошие» данные (несжимаемые / повторяющиеся / текст).

Без бенчмарков оптимизация превращается в угадайку.

## 2) Главные источники затрат в LZMA/LZMA2

- Match finder (хеши, бинарные деревья/цепочки)
- Range coder (ветвления, доступ к probability arrays)
- Copy/дикшенари операции

## 3) Быстрые выигрыши в C#

- `ArrayPool<byte>` для больших буферов
- `Span<byte>`/`ReadOnlySpan<byte>`
- сокращение проверок границ за счёт срезов `Span` и локальных переменных (проект принципиально
  **без `unsafe`** — этот путь оптимизации не используем)
- `MethodImplOptions.AggressiveInlining` в микро‑функциях
- избегаем `MemoryStream.ToArray()` в горячем пути

## 4) SIMD

Реалистичные цели SIMD:

- ускорить сравнение матчей (memcmp/longest common prefix)
- ускорить копирование (если не хватает `Buffer.MemoryCopy`)

Range coder SIMD‑ится плохо (слишком ветвисто).

## 5) Многопоток

LZMA внутри блока последовательный, но можно:

- сжимать **независимые блоки** параллельно (reset dictionary)
- сжимать разные файлы параллельно (non-solid)

Solid‑режим — опционально.

## 6) GPU (GPGPU)

Честно: LZMA плохо ложится на GPU из‑за зависимости по данным.

Но GPU может быть полезен для:

- CRC32/хэши (если это реально bottleneck)
- фильтры (BCJ, delta)
- «батч» компрессия множества маленьких файлов (параллельно, но это спорно)

Поэтому GPU — после того, как CPU версия уже быстрая и измеренная.


## 7) Крипта (ГОСТ) — отложенные оптимизации

Замеры — в [`bench/BASELINE.md`](../bench/BASELINE.md), раздел «Крипта» (2026-07-17).

**Статус:** ✅ сделано — расписание ключа ГОСТ вынесено из пер-блочного пути (считается один раз на
CTR-преобразование). Дало Кузнечику ×4.6 (0.04 → 0.2 МиБ/с), корректность цела.

**⏳ ОТЛОЖЕНО (низкий приоритет): T-таблица для Кузнечика.** Даже после фикса managed-Кузнечик ~0.2 МиБ/с —
доминирует линейная L-функция (GF(2⁸)-умножение в цикле, 9 раундов). Классическая оптимизация —
предвычислить композицию `L∘S` как 16 таблиц по 256×16 байт (T-таблицы), тогда раунд = 16 табличных
выборок + XOR. Ожидаемо: десятки-сотни МиБ/с. Работа отдельная, средняя по объёму.

**Почему отложено (решение Артемия 2026-07-17):** ГОСТ — исследовательская ветка; боевая крипта в
Gov-редакции идёт через сертифицированный криптопровайдер (см. [`PROVENANCE.md`](PROVENANCE.md)), а не
через наш managed-ГОСТ. Вернуться, если появится конкретная потребность (например, managed-Кузнечик для
Community-редакции). AES (боевой путь 7zAES) уже на скорости железа (~1.3 ГиБ/с) — оптимизировать нечего.
