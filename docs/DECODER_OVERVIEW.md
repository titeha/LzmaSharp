# Обзор декодера LZMA / LZMA2

## Назначение документа

Этот документ описывает низкоуровневую часть декодера LZMA / LZMA2.

Он нужен как карта местности для кода, который изначально ориентирован на поведение LZMA SDK и поэтому местами выглядит не как обычный высокоуровневый C#:

- много явного состояния;
- ручная работа с буферами;
- минимум лишних аллокаций;
- конечные автоматы;
- аккуратное различение `Ok`, `NeedMoreInput`, `InvalidData` и `NotSupported`.

Документ не описывает весь контейнер 7z. За общую архитектуру 7z отвечают `ARCHITECTURE.md`, `ROADMAP.md` и `STAGE1_STATUS.md`.

## Основные слои

В декодировании LZMA2 участвуют два уровня.

### LZMA2

LZMA2 — это контейнер из чанков.

Он отвечает за:

- чтение управляющих байтов;
- чтение размеров упакованных и распакованных данных;
- переключение между copy-чанками и LZMA-чанками;
- сброс словаря;
- сброс LZMA-состояния;
- передачу LZMA payload во вложенный LZMA-декодер.

### LZMA

LZMA — это собственно range coder + LZ77-логика.

Он отвечает за:

- декодирование битового потока;
- работу с probability arrays;
- восстановление literal-байтов;
- восстановление match-последовательностей;
- копирование данных из словаря назад по distance.

## Главные сущности

### `CLzma2Dec`

Состояние LZMA2-декодера.

Ключевые поля:

- `State` — текущее состояние автомата чтения чанка;
- `Control` — управляющий байт текущего чанка;
- `UnpackSize` — сколько байт нужно выдать из текущего чанка;
- `PackSize` — сколько байт packed data нужно прочитать для LZMA-чанка;
- `NeedInitDic` — требуется ли инициализация / сброс словаря;
- `NeedInitState` — требуется ли сброс состояния LZMA;
- `TempBuf` / `TempBufSize` — временный буфер для неполных заголовков;
- `Decoder` — вложенный LZMA-декодер.

### `CLzmaDec`

Состояние LZMA-декодера.

Ключевые поля:

- `Dic` — выходной словарь;
- `DicPos` — текущая позиция в словаре;
- `DicBufSize` — размер словаря;
- `Prop` — свойства LZMA `lc`, `lp`, `pb`;
- `Probs` — массив вероятностей range coder-а;
- `TempBuf` / `TempBufSize` — временные байты для инициализации range coder-а.

## Общий цикл `Lzma2Dec.DecodeToDic`

`DecodeToDic` можно воспринимать как цикл по чанкам LZMA2.

### 1. Чтение заголовка чанка

Если декодер ещё не находится в состоянии данных, он читает заголовок чанка:

1. `Control`;
2. `UnpackSize`;
3. `PackSize`, если это LZMA-чанк;
4. `Prop`, если текущий control требует новых свойств LZMA.

Если вход закончился посередине заголовка, декодер сохраняет частичные данные в `TempBuf` и возвращает `NeedMoreInput`.

### 2. Copy-чанк

Если `Control` обозначает uncompressed / copy-чанк, декодер просто копирует данные во внешний словарь.

Для copy-чанка важно:

- не выйти за входной буфер;
- не выйти за выходной словарь;
- корректно уменьшить `UnpackSize`;
- при недоборе входа вернуть `NeedMoreInput`, а не упасть исключением.

### 3. LZMA-чанк

Если `Control >= 0x80`, декодер запускает вложенный LZMA-декодер.

Перед этим по `Control` определяется:

- нужно ли сбросить словарь;
- нужно ли сбросить LZMA-состояние;
- нужно ли прочитать новые свойства `lc/lp/pb`.

Затем вызывается LZMA-декодер с ограничениями:

- не больше `UnpackSize` выходных байт;
- не больше `PackSize` входных байт.

### 4. Завершение чанка

Когда `UnpackSize` для текущего чанка становится равен нулю, чанк завершён.

Декодер возвращается к состоянию чтения следующего `Control`.

### 5. Конец потока

`Control == 0x00` означает конец LZMA2-потока.

После этого декодер должен завершить поток согласованным результатом, а не пытаться читать следующие поля заголовка.

## `Parse` и `TempBuf`

`Parse(...)` нужен для сценариев, где вход может приходить кусками.

Он:

- докачивает заголовок чанка в `TempBuf`;
- обновляет `State`;
- обновляет `PackSize`;
- обновляет `UnpackSize`;
- возвращает `NeedMoreInput`, если данных пока недостаточно.

`TempBuf` особенно важен для streaming-сценариев: нельзя предполагать, что заголовок чанка всегда целиком доступен в одном входном буфере.

## Проверка первого байта LZMA payload

Для LZMA payload внутри LZMA2 есть важная проверка: первый байт range coder-а должен быть `0x00`.

Если он не равен нулю, это почти всегда означает повреждённый поток или неправильное смещение при чтении.

Такие ошибки обычно проявляются как `InvalidData`.

## Почему много проверок размеров

В LZMA / LZMA2 много проверок вокруг размеров, потому что поток содержит несколько независимых ограничений:

- сколько байт можно прочитать из текущего packed chunk;
- сколько байт нужно выдать из текущего unpacked chunk;
- сколько места есть в словаре;
- не закончился ли вход посередине range coder-а;
- не получилась ли невозможная LZMA match-длина;
- не указывает ли match назад за пределы допустимой истории.

Эти проверки не являются лишними. Они защищают декодер от повреждённых данных и от рассинхронизации автомата.

## Где смотреть при отладке

Если проблема в заголовке LZMA2-чанка, смотреть:

- `Control`;
- `State`;
- `UnpackSize`;
- `PackSize`;
- `NeedInitDic`;
- `NeedInitState`;
- `TempBufSize`.

Если проблема в LZMA payload, смотреть:

- первые 8–16 байт payload-а;
- `DicPos`;
- `processedPos`;
- `checkDicSize`;
- `range`;
- `code`;
- текущие свойства `lc/lp/pb`.

Если падает copy-чанк, смотреть:

- сколько байт осталось во входе;
- сколько байт осталось в `UnpackSize`;
- хватает ли места в словаре.

## Типовые причины `InvalidData`

Частые причины ошибки данных:

- неверный `Control`;
- неожиданный конец входа;
- некорректный первый байт LZMA payload;
- невозможные LZMA свойства;
- невозможная match-длина;
- distance указывает за пределы словаря;
- packed chunk заканчивается раньше ожидаемого;
- unpacked chunk не набирает ожидаемый размер;
- поток продолжает содержать ненулевые данные там, где ожидается допустимый padding.

## Типовые причины `NeedMoreInput`

`NeedMoreInput` означает не ошибку формата, а нехватку входных данных для продолжения.

Типовые случаи:

- заголовок LZMA2-чанка пришёл не полностью;
- copy-чанк пришёл не полностью;
- LZMA payload пришёл не полностью;
- range coder не получил достаточно байтов для продолжения.

## Типовые причины `NotSupported`

`NotSupported` означает, что вход может быть валидным для формата, но текущая реализация не поддерживает этот сценарий.

Для низкоуровневого LZMA / LZMA2 это может относиться к тем режимам, которые ещё не реализованы или намеренно не входят в текущий этап проекта.

Для контейнера 7z это чаще относится к неподдерживаемым coder-ам, topology-сценариям или AES.

## Правило изменения декодера

При изменении низкоуровневого декодера важно соблюдать порядок:

1. сначала понять, какой инвариант меняется;
2. добавить или обновить тест;
3. проверить обычные сценарии;
4. проверить повреждённые данные;
5. только потом оптимизировать.

Оптимизация без тестов в этой зоне рискованна: маленькое изменение в автомате состояний может сломать streaming, `NeedMoreInput` или обработку повреждённого входа.
