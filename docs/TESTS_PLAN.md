# План тестирования

Этот документ описывает **философию и правила** тестирования. Перечень конкретных тестов —
это сам код в `tests/Lzma.Core.Tests`; сводки покрытия по этапам — в соответствующих
stage-документах ([`STAGE1_STATUS.md`](STAGE1_STATUS.md), [`STAGE15_AES_STATUS.md`](STAGE15_AES_STATUS.md),
[`STAGE16_GOST_STATUS.md`](STAGE16_GOST_STATUS.md), [`STAGE2_WRITER_STATUS.md`](STAGE2_WRITER_STATUS.md)).

Фреймворк: `xUnit` v3 (пакет `xunit.v3` 3.2.2). Тестовые проекты являются исполняемыми
(`OutputType Exe`), поэтому поддерживаются оба способа запуска: `dotnet test` (через
`xunit.runner.visualstudio`) и прямой запуск собранного исполняемого файла.

Динамический пропуск теста выполняется только через `Assert.Skip("причина")` — причина видна
в отчёте прогона. Тихий `return` из теста запрещён: он даёт ложно-зелёный результат.

Применено на практике: четыре теста Windows-специфичных правил (коллизия регистра, недопустимые
символы, зарезервированные имена, перезапись файла с атрибутом `ReadOnly`) на других ОС
фиксируются как видимые пропуски с причиной, а не как пройденные; сценарий смены рабочего каталога
пропускается видимым образом, если сборка-проба `Lzma.Ui.CwdProbe` не собрана.

Техническая деталь: `Assert.Skip` в xUnit v3 не помечен `[DoesNotReturn]`, поэтому в helper-методе
со строковым возвратом после вызова пропуска требуется недостижимый `return null!;`
(иначе ошибка компиляции `CS0161`).

## Структура тестов

Группы повторяют структуру библиотеки: `Checksums`, `Lzma1`, `Lzma2`, `SevenZip`.

Зона `SevenZip` дополнительно разбита по смыслу, и эти группы должны оставаться легко
находимыми:

- корректность archive reader;
- обработка encoded header;
- разбор `StreamsInfo` / `FilesInfo` / `PackInfo` / `SubStreamsInfo`;
- поведение folder decoder и archive decoder;
- интеграционные цепочки coder-ов;
- безопасность распаковки;
- совместимость на реальных `.7z`-архивах;
- writer-path;
- неподдерживаемые, но явно отслеживаемые сценарии (AES/GOST/прочее).

Если группа разрастается — лучше выделить её в отдельный файл с понятным именем, чем
смешивать с существующими сценариями.

## Текущее состояние покрытия

Decoder-path (этап 1) покрыт unit-, интеграционными и real-archive тестами для основного
поддерживаемого подмножества без AES; `SevenZipFolderDecoder` покрыт прямыми тестами по
основным веткам (одиночные coder-ы, BCJ2, topology, размеры, negative-path). AES (этап 1.5)
и GOST (этап 1.6) покрыты согласно их stage-документам. Writer и энкодер (этап 2) — согласно
[`STAGE2_WRITER_STATUS.md`](STAGE2_WRITER_STATUS.md).

Основной объём тестовой стабилизации decoder-path выполнен. Новые synthetic-тесты дальше
добавляются только при наличии конкретного риска, а не ради полного перебора комбинаций.

## Правила добавления тестов

- Одно маленькое изменение — один соответствующий маленький тест.
- Предпочитать понятные синтетические фикстуры огромным непрозрачным бинарникам.
- Реальные `.7z`-файлы использовать там, где важна совместимость на уровне контейнера.
- Если имя теста перестало соответствовать коду — переименовывать сразу.
- Не добавлять synthetic edge-case тесты без явной причины.

Новый тест должен закрывать хотя бы один из рисков:

- безопасность распаковки;
- crash / exception path;
- публичный контракт результата `Ok` / `InvalidData` / `NotSupported`;
- ветку, которую реально можно сломать при оптимизации или рефакторинге;
- поведение на реальном архиве.

## Особые требования по областям

### AES

Для AES-сценариев обязательны проверки: успешное чтение с правильным паролем; `NotSupported`
без пароля; `InvalidData` при неверном пароле или повреждённых данных; отсутствие записи на
диск при ошибке; сохранение поведения обычных нешифрованных архивов. Real-archive фикстуры
создаются настоящим `7z` (генераторы — в `tools/TestArchiveGenerators`, архивы — в
`TestData/Real`).

### GOST

GOST тестируется synthetic-архивами: стандартный 7-Zip не используется, потому что
GOST-поддержка экспериментальная, использует private method id и несовместима с ним.

### Writer / encoder (этап 2)

Обязательны round-trip тесты, структурные проверки через `SevenZipArchiveReader`,
проверки декодируемости через decoder-path и negative-тесты на неподдерживаемые/некорректные
сценарии. По мере появления реального сжатия — тесты совместимости в обе стороны (наше
кодирование ↔ эталонная реализация). Тесты добавляются только под реализуемый сценарий.

### Собственные codec-реализации

Когда временные внешние зависимости начнут заменяться собственными реализациями (`PPMd`,
`BZip2`, `Deflate`, `Deflate64`, возможные ZIP-сценарии), для каждого codec-а нужны: тесты
на эталонных данных; roundtrip-тесты при наличии encoder-а; тесты совместимости на реальных
архивах; negative-тесты на повреждённый поток; тесты на граничные размеры; проверка, что
внешний контракт `SevenZipFolderDecoder` не меняется при замене реализации.

### Fault-injection harness (test-only)

Test-only помощники fault injection живут в `tests/Lzma.Core.Tests/Helpers` и используются
в security-фазах regression harness:

- `ThrowBeforeCrossingWriteStream` — test-only поток, бросающий исключение до пересекающей
  лимит записи, со sticky injected failure; не моделирует physical partial write внутри
  одного вызова;
- контракт helper-а закреплён targeted-тестами синхронных/асинхронных сценариев
  (перечень — в коде);
- это test-harness-статус: сам по себе он не означает, что transactional создание архивов
  (SEC-002) реализовано; production-статус SEC-002 отслеживается отдельно в
  `docs/plans/SECURITY_REMEDIATION_PLAN.md` §4.5.

Для staged-томов (`Lzma.Ui`) используется отдельный fake файловых операций
`StagedFileOperationsFake` (вложен в `tests/Lzma.Ui.Tests/StagedVolumeSetTests.cs`):

- отказ инъектируется по **сквозному 0-индексу** всех вызовов `Move` (backup / publish / restore),
  поэтому фазы различаются порядком вызовов, а не флагами; точек отказа может быть несколько;
- исключение бросается **до** реального переноса, а вызов всё равно попадает в журнал
  `MoveCalls` — это даёт наблюдаемое доказательство того, какие попытки состоялись;
- для всех прочих вызовов выполняется настоящий `File.Move`, имитация переноса запрещена;
- дублирующийся индекс отказа — ошибка конфигурации fake, а не «последний wins»;
- journal `DeleteCalls` позволяет проверять, что уцелевшая резервная копия не удаляется.

### Interop с внешним 7-Zip (явное требование, без тихого пропуска)

Тесты, сверяющие результат с настоящим 7-Zip, обязаны выполняться, а не молча завершаться:

- путь к исполняемому файлу даёт helper `tests/Lzma.Core.Tests/Helpers/SevenZipInterop.cs`
  (`RequireExecutable()`): `SEVENZIP_PATH` → `7zz` в PATH → `7z` в PATH →
  `C:\Program Files\7-Zip\7z.exe` на Windows;
- если ничего не найдено, helper бросает исключение с перечнем проверенных кандидатов и
  подсказкой по установке для трёх ОС — тест падает, а не становится ложно-зелёным;
- в CI 7-Zip устанавливается шагом workflow (ubuntu/macos — официальный `7zz` из релиза
  ip7z/7zip, Windows — предустановленный либо Chocolatey), а шаг evidence печатает
  фактическую версию и путь;
- локально переменная `SEVENZIP_PATH` позволяет указать конкретный бинарник (например,
  для проверки на другой версии 7-Zip).

### CWD-сценарии (изолированный процесс)

`Environment.CurrentDirectory` — состояние процесса, а xUnit выполняет тесты параллельно,
поэтому менять CWD внутри тест-раннера запрещено. Сценарии, где поведение зависит от CWD
(например, validate/use consistency относительных путей в `StagedVolumeSet`), выполняются
в отдельном test-only процессе-пробе `tests/Lzma.Ui.CwdProbe`:

- проба входит в `LzmaSharp.sln` и собирается вместе с решением;
- тест-родитель запускает её с явным `WorkingDirectory`, получает код возврата и
  stdout/stderr, а инварианты проверяет по фактическому состоянию файловой системы
  (байты, состав каталогов), а не по сообщениям production-кода;
- если сборка пробы не найдена, тест падает с явным сообщением и перечнем проверенных путей:
  тихий пропуск запрещён, так как даёт ложно-зелёный результат;
- временные каталоги удаляются в `finally`.

### Платформенно-зависимые theory-данные (Windows-only)

Некоторые theory-тесты содержат данные, которые имеют смысл только на Windows.
Это не тихий пропуск (TST-001), а осознанное ограничение: данные не генерируются
на не-Windows платформах, поэтому xUnit не обнаруживает соответствующие кейсы.

**`SevenZipArchiveDecoderExtractUnsafePathTests.InvalidEntryNames()`**
(`tests/Lzma.Core.Tests/SevenZip/Decoding/SevenZipArchiveDecoderExtractUnsafePath.Tests.cs`):

- `"C:/evil.bin"` — абсолютный путь с буквой диска; на POSIX это относительный путь
  (сегмент `C:`), не являющийся небезопасным.
- `"file.bin:ads"` — NTFS Alternate Data Stream; на POSIX `:` — легальный символ имени.

Эти 2 кейса обнаруживаются только на Windows, что объясняет разницу в общем числе тестов
`Lzma.Core.Tests`: 1738 (Windows) vs 1736 (Linux/macOS). Разница не является дефектом
или скрытым пропуском — это корректное отражение платформенно-специфичной семантики
безопасности.

Аналогичные Windows-only тесты (коллизия регистра, недопустимые символы, зарезервированные
имена, перезапись файла с атрибутом `ReadOnly`, успешная перезапись `ReadOnly`-файла без
остатков backup) используют видимый пропуск:
`if (!OperatingSystem.IsWindows()) Assert.Skip("причина");` — они обнаруживаются на всех
платформах, выполняются только на Windows, а на других ОС фиксируются как пропущенные
с указанием причины. Поэтому на POSIX ожидается 1731 passed / 5 skipped (всего 1736).
На Windows пропусков нет: интеграционный тест длинного пути (~300 символов) выполняется
на всех трёх ОС, потому что файловые вызовы маршрута переводятся на расширенную форму `\\?\`
и лимит Windows поднят до расширенного предела. Отдельный тест проверяет охрану `overwrite: false`
на длинном пути — это страховка от асимметрии обёрток: если проверка существования останется
без префикса, а публикация с префиксом, охрана перестанет срабатывать.
Тихий `return` из теста запрещён: он даёт ложно-зелёный результат.
Это отдельная проблема TST-001, которая отслеживается в рамках security-remediation
и будет устранена отдельным шагом (миграция на xUnit v3 `Assert.SkipWhen` или
выделение в Windows-only тест-проект).
