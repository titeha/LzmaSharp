# Правила проекта LzmaSharp

## Область проекта

- Основной язык: C#.
- `Lzma.Core` ориентирован на `net8.0`.
- Тестовый проект и UI в текущем состоянии ориентированы на `net10.0`.
- Перед использованием API проверяй `TargetFramework` конкретного проекта.
- Не используй в `Lzma.Core` API, отсутствующие в `net8.0`.
- Тесты: xUnit.
- Изменения безопасности выполняются небольшими независимыми этапами.

## Код и тесты

- Для исправления функционального дефекта сначала найди существующий тест
  либо добавь минимальный тест, воспроизводящий дефект.
- Новый тест должен падать из-за исправляемого поведения, а не только
  из-за ошибки компиляции.
- Если автоматическое воспроизведение технически невозможно, явно укажи
  причину и предложи проверяемый альтернативный критерий.
- Документационные, конфигурационные и чисто стилевые изменения не требуют
  искусственного функционального теста; для них выполняются соответствующие
  сборочные, статические или ручные проверки.
- Не считать ошибку компиляции воспроизведением функционального дефекта.
- Не удалять, не пропускать и не ослаблять существующие тесты.
- Для файловых операций проверять отмену, исключения, очистку временных файлов
  и сохранность ранее существовавших данных.
- Для размеров, счётчиков и смещений исключай переполнение:
  используй `checked` либо сравнения, не требующие потенциально
  переполняющегося сложения.
- Не выделяй память на основании недоверенного размера из архива без
  предварительной проверки лимита.
- Все зависящие от входных данных выделения должны быть ограничены
  утверждённым resource budget.
- Не смешивать исправление дефекта с архитектурным разделением проектов.

## Безопасность

- Не проектировать собственные криптографические конструкции.
- GOST остаётся Experimental до отдельного утверждённого формата.
- CRC не считать криптографическим MAC.
- Не заявлять защиту от symlink, junction или TOCTOU без соответствующих
  платформенных тестов.
- Не заявлять транзакционность без тестов отказа и rollback.
- Не заявлять bounded-memory только на основании потокового API.

## Git

Перед изменением выполнить:

- `git status --short`;
- проверку активной ветки.

Перед завершением выполнить:

- `git diff --check`;
- `git diff --name-only`;
- сначала целевые тесты;
- полный `dotnet test` — один раз перед завершением задачи, если изменён
  production-код;
- если полный набор уже имел baseline-ошибки до начала работы, не исправляй
  их попутно: перечисли отдельно.

Commit создаётся только по прямой команде пользователя.
