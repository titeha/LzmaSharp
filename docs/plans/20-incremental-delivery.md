# Маленькие контролируемые шаги

Это постоянное правило проекта LzmaSharp.

## 1. Основной принцип

Не ломай то, что уже работает.

Любая задача выполняется как последовательность маленьких проверяемых шагов.
Следующий шаг начинается только после зелёной проверки предыдущего.

## 2. Ограничение шага

Один шаг должен иметь:

- одну причину изменения;
- одну проверяемую цель;
- не более двух production-файлов;
- не более одного test-файла;
- один targeted test command;
- отдельный commit после проверки.

Если задача больше — сначала составь список микрошагов и выполни только
первый утверждённый шаг.

## 3. Создание нового файла

Новый файл создавай по фазам:

1. Каркас:
   - namespace;
   - type;
   - constructor;
   - fields/properties;
   - required abstract members;
   - `NotImplementedException("STEP_N")` в функциональном месте.
   - Проверка: build.

2. Ровно одна функция или overload.
   - Проверка: build.

3. Тесты только этой функции:
   - positive;
   - boundary;
   - negative/failure.
   - Проверка: targeted tests.

4. Следующая функция — только после зелёного предыдущего шага.

Не создавай сразу полный framework, все overloads и всю test matrix.

## 4. Изменение существующего кода

- Сначала characterization или failing regression test.
- Изменяй минимальный участок.
- Не переписывай соседние зелёные функции.
- Не объединяй security fix, refactor и style cleanup.
- Не меняй public API без отдельного согласования.

## 5. Поведение при ошибке

После ошибки:

1. прочитай точную ошибку;
2. внеси одно минимальное исправление;
3. повтори минимальную проверку.

Максимум два цикла исправления одной проблемы.

После второго неуспеха:

- остановись;
- не начинай задачу заново;
- не переписывай всё с нуля;
- сохрани текущий diff;
- верни `BLOCKED`.

## 6. Проверка

После микрошагa:

```text
git diff --check
git diff --name-only
build затронутого проекта
targeted tests
```

Полный suite выполняется один раз перед завершением production-задачи.

## 7. Review gate

Перед commit попроси read-only critic review.

Critic не редактирует код. Он возвращает:

- `APPROVE`;
- либо `REQUEST_CHANGES` с точным файлом, строкой, нарушенным инвариантом
  и минимальной правкой.

После `REQUEST_CHANGES` допускается один correction step и повторный review.

Не запускай бесконечный цикл «до совершенства».
Максимум два review rounds.

## 8. Commit

Commit создаётся только когда:

- allowlist соблюдён;
- build зелёный;
- targeted tests зелёные;
- critic дал `APPROVE`;
- пользователь явно разрешил commit.
