# Архитектура

Этот документ описывает **архитектуру** проекта: компоненты, их зоны ответственности,
пайплайн и контракты. Текущий статус по этапам (что именно поддержано) живёт в
stage-документах — см. [`ROADMAP.md`](ROADMAP.md) и ссылки оттуда.

## Цель

Проект строится как понятное управляемое ядро на C# для LZMA / LZMA2 / 7z.

Приоритет текущего этапа — развитие writer / encoder-направления без переписывания уже
стабилизированного decoder-path. Корректность, предсказуемое поведение и безопасность
распаковки — обязательные требования. Оптимизация — отдельный последующий этап,
опирающийся на тесты и профилирование.

## `Lzma.Core`

Основная библиотека проекта. Внутри неё:

- низкоуровневые алгоритмы и модели данных;
- декодеры и инкрементальные декодеры;
- энкодеры LZMA / LZMA2 (см. ниже);
- компоненты чтения контейнера 7z;
- writer-path 7z;
- логика безопасной распаковки.

### `Checksums`

CRC и вспомогательные вычисления целостности данных.

### `Lzma1`

LZMA / LZMA-Alone: декодер, инкрементальный декодер, энкодер и его подкомпоненты
(range coder, литералы, длины, дистанции, bit-tree).

### `Lzma2`

LZMA2: разбор чанков и блоков, декодер, инкрементальный декодер, энкодеры (`Copy`,
LZMA-чанки).

### `SevenZip`

Контейнер 7z: чтение signature/next header, разбор `StreamsInfo` и `FilesInfo`,
декодирование encoded header и folder-ов, сборка декодированных записей, безопасная
распаковка на диск, writer-path.

## `Lzma.Core.Tests`

Проект тестов на `xUnit`. Группы повторяют структуру библиотеки: `Checksums`, `Lzma1`,
`Lzma2`, `SevenZip`. Зона `SevenZip` дополнительно разбита по смыслу: reader, encoded
header, streams info, files info, folder decoder, archive decoder, writer-path,
безопасность распаковки, реальные `.7z`-архивы, явно неподдерживаемые сценарии.
Правила тестирования — в [`TESTS_PLAN.md`](TESTS_PLAN.md).

## `vendor/lzma-sdk`

Эталонные исходники для сверки поведения, анализа формата и проверки пограничных случаев.
Это не основная реализация проекта — цель проекта — собственное управляемое C#-ядро.

## Основной путь декодирования 7z

Концептуально чтение и распаковка делятся на уровни:

1. проверка signature header;
2. чтение next header;
3. разбор `StreamsInfo`;
4. разбор `FilesInfo`;
5. декодирование encoded header, если он есть и поддерживается;
6. декодирование folder через `SevenZipFolderDecoder`;
7. сборка логических записей архива;
8. валидация путей вывода;
9. запись файлов и директорий на диск.

Каждый уровень возвращает явный результат: `Ok`, `InvalidData`, `NeedMoreInput`,
`NotSupported`. Исключения не должны быть обычным способом управления потоком для
ожидаемых ошибок формата.

### `SevenZipArchiveReader`

Читает структуру архива: signature header, next header, packed streams, decoded header
metadata. Не занимается записью на диск — это задача более высокого уровня.

### `SevenZipArchiveDecoder`

Преобразует прочитанную структуру в декодированные записи: проходит по folder-ам,
вызывает `SevenZipFolderDecoder`, сопоставляет распакованные потоки с файлами, применяет
метаданные, готовит результат для decode/extract API.

### `SevenZipFolderDecoder`

Центральная точка декодирования цепочек coder-ов внутри folder: проверка topology, выбор
packed stream, одиночные coder-ы, линейные цепочки, BCJ2, проверка размеров, согласованные
результаты `Ok` / `InvalidData` / `NotSupported`. Поддерживаемые ветки — см.
[`STAGE1_STATUS.md`](STAGE1_STATUS.md) (методы и фильтры), [`STAGE15_AES_STATUS.md`](STAGE15_AES_STATUS.md)
(AES) и [`STAGE16_GOST_STATUS.md`](STAGE16_GOST_STATUS.md) (GOST).

Изменения в этом компоненте сопровождаются тестом, если меняют публичный контракт,
error-path или поведение на реальном архиве.

## Безопасность распаковки

Распаковка на диск — отдельная зона риска. Перед записью файлов проект валидирует:

- абсолютные пути и относительные пути с выходом за целевую директорию;
- недопустимые символы и зарезервированные имена Windows;
- конфликт файлов и директорий, дублирующиеся пути, коллизии по регистру;
- недопустимые времена файлов;
- любые сценарии, ведущие к записи вне целевой директории.

Главное правило: архив не должен иметь возможности записать данные туда, куда пользователь
явно не разрешал.

## AES decoder-path

AES добавлен как слой перед обычным декодированием packed stream-ов:

1. определяется AES coder и разбираются его свойства;
2. пароль передаётся через явный `SevenZipDecodeOptions` (UTF-16LE без BOM);
3. выполняется key derivation по правилам 7zAES;
4. строится полный IV из AES properties;
5. packed stream расшифровывается через AES-256-CBC;
6. расшифрованные данные передаются в обычный pipeline `SevenZipFolderDecoder`.

Компоненты: `SevenZipAesCoder`, `SevenZipAesProperties`, `SevenZipPassword`,
`SevenZipAesKeyDerivation`, `SevenZipAesInitializationVector`, `SevenZipAesDecryptor`,
`SevenZipAesPackedStreamDecryptor`, `SevenZipDecodeOptions`. Подключён в
`SevenZipFolderDecoder`, `SevenZipEncodedHeaderDecoder`, `SevenZipArchiveReader`,
`SevenZipArchiveDecoder`.

Контракт ошибок: без пароля — `NotSupported`; неверный пароль или повреждённые данные —
`InvalidData`; неподдерживаемый AES-сценарий — `NotSupported`. Ошибка AES не должна
создавать файлы или директории на диске. Покрытые сценарии — в
[`STAGE15_AES_STATUS.md`](STAGE15_AES_STATUS.md).

Запись AES-архивов в текущую реализацию не входит.

## Экспериментальная GOST-ветка

GOST — экспериментальное decoder-only расширение LzmaSharp: private method id,
несовместимо со стандартным 7-Zip. Подключено в decode-path через `SevenZipFolderDecoder`.
Поддержанный сценарий: Kuznyechik + CTR + IV + direct-key KDF, расшифровка packed
stream-ов, encrypted header. Детали и ограничения — в
[`STAGE16_GOST_STATUS.md`](STAGE16_GOST_STATUS.md).

## Writer-path 7z

На этапе 2 развивается writer-path. Он отделён от decoder-path и не переписывает логику
чтения и декодирования. Текущий перечень поддержанных сценариев и контракты имён/путей —
в [`STAGE2_WRITER_STATUS.md`](STAGE2_WRITER_STATUS.md); здесь описана только архитектура.

### Публичный вход

- `SevenZipArchiveWriter.BuildArchive(...)` — основной вход;
- `SevenZipArchiveWriterEntry` — входная модель (имя, содержимое, признак директории,
  опциональные Windows attributes, опциональное `LastWriteTimeUtc`);
- `SevenZipArchiveWriteResult` — результат операции.

### Маршрутизация

После входной validation writer выбирает путь построения:

- пустой набор entry → пустой архив;
- набор без файловых данных → empty-entry path (только header-структура: `FilesInfo`,
  `EmptyStream`, `EmptyFile`, имена);
- набор с непустыми файлами → `Copy` path (packed data + `PackInfo` + `UnpackInfo` только
  для непустых файлов; `FilesInfo` описывает все entry);
- некорректные входные данные → `InvalidData`.

### Контракт ошибок writer-а

- `Ok` — архив успешно построен;
- `InvalidData` — некорректные входные данные (null, некорректный path, директория с
  данными, дубли/конфликты имён, несогласованные attributes, не-UTC `LastWriteTimeUtc`);
- `NotSupported` — сценарий распознан, но пока не входит в поддержанный writer-path;
- `InternalError` — неожиданное внутреннее состояние.

Writer не должен молча создавать частично некорректный архив. Имена и вложенные пути
проходят validation, нацеленную на безопасную распаковку (в том числе на case-insensitive
файловых системах); конкретные правила — в [`STAGE2_WRITER_STATUS.md`](STAGE2_WRITER_STATUS.md).

Существующий decoder-path используется как проверка результата writer-а через
`SevenZipArchiveReader`, `SevenZipArchiveDecoder` и round-trip тесты.

## Энкодер

В `Lzma1` / `Lzma2` реализована низкоуровневая машинерия LZMA-кодирования: range encoder,
энкодеры литералов / длин / дистанций / bit-tree, `LzmaAloneEncoder` и инкрементальный
вариант, `Lzma2LzmaEncoder` (нарезка на чанки + COPY-fallback), `Lzma2CopyEncoder`. Всё
покрыто round-trip тестами через собственный декодер.

Ключевое архитектурное ограничение текущего шага: **match finder отсутствует**.
`LzmaEncoder` «скриптовый» — кодирует литералы и matches по явно заданным
`(distance, length)`, но сам совпадения не ищет. Реальное сжатие произвольных данных
появится после добавления match finder-а (план — [`ENCODER_MVP_PLAN.md`](ENCODER_MVP_PLAN.md)).

Архитектурные требования к энкодеру:

- независимость от тестовых helper-ов;
- совместимость с эталонными реализациями;
- roundtrip-тесты и возможность записи 7z-контейнера;
- сохранение читаемости кода до начала оптимизации.

## API-направление

Текущий фокус:

- работа с `byte[]`, `ReadOnlySpan<byte>` и `Span<byte>` внутри ядра;
- декодирование архива в память и безопасная распаковка на диск через high-level API;
- передача пароля для AES через `SevenZipDecodeOptions`;
- явные результаты вместо неявных исключений для ожидаемых ошибок данных.

Долгосрочно: stream-friendly API там, где это улучшает сценарии; меньше копирований;
аккуратное управление буферами; ядро как библиотека без привязки к UI.

## Оптимизация

Оптимизация — не цель этапов 1 и 2. Порядок фиксированный: корректность → тесты →
профилирование → точечная оптимизация. Допустимые направления и инструменты — в
[`PERFORMANCE_PLAN.md`](PERFORMANCE_PLAN.md). Низкоуровневая оптимизация не должна ухудшать
читаемость публичной логики без измеримой причины.

## Правило изменения архитектуры

Любое существенное изменение архитектуры должно отвечать на вопросы:

- какой сценарий оно улучшает;
- какой риск закрывает;
- какие тесты подтверждают поведение;
- не ухудшает ли оно безопасность распаковки;
- не смешивает ли уровни ответственности.

Маленькие проверяемые изменения предпочтительнее больших переписываний.
