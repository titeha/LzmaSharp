# Архитектура

## Цель

Проект строится как понятное управляемое ядро на C# для LZMA / LZMA2 / 7z.

Главный приоритет текущего этапа — постепенное развитие writer-path без переписывания уже стабилизированного decoder-path.

Корректность, предсказуемое поведение и безопасность распаковки остаются обязательными требованиями. Оптимизация остаётся отдельным последующим этапом и должна опираться на тесты и профилирование.

## `Lzma.Core`

`Lzma.Core` — основная библиотека проекта.

Внутри неё находятся:

- низкоуровневые алгоритмы;
- модели данных;
- декодеры;
- вспомогательные компоненты чтения контейнера;
- минимальный writer-path для поддержанных сценариев 7z;
- логика безопасной распаковки.

Зона контрольных сумм.

- начальный задел под энкодер.

Включает:

- чтение next header;
- разбор `StreamsInfo`;

- декодирование encoded header для поддерживаемых сценариев;

Эта папка не является основной реализацией проекта. Основная цель проекта — собственное управляемое C#-ядро.

## Основной путь декодирования 7z

Концептуально путь чтения и распаковки 7z делится на несколько уровней.

1. Проверка signature header.
2. Чтение next header.
3. Разбор `StreamsInfo`.
4. Разбор `FilesInfo`.
5. Декодирование encoded header, если он есть и поддерживается.
6. Декодирование folder через `SevenZipFolderDecoder`.
7. Сборка логических записей архива.
8. Валидация путей вывода.
9. Запись файлов и директорий на диск.

Каждый уровень должен возвращать явный результат:

- `Ok`;
- `InvalidData`;
- `NeedMoreInput`;
- `NotSupported`.

Исключения не должны быть обычным способом управления потоком для ожидаемых ошибок формата.

## `SevenZipArchiveReader`

`SevenZipArchiveReader` отвечает за чтение структуры архива.

Его зона ответственности:

- signature header;
- next header;
- packed streams;
- decoded header metadata;
- передача структурированных данных следующему уровню.

Reader не должен заниматься безопасной записью на диск. Это задача более высокого уровня.

## `SevenZipArchiveDecoder`

`SevenZipArchiveDecoder` отвечает за преобразование прочитанной структуры архива в декодированные записи.

Его зона ответственности:

- пройти по folder-ам;
- вызвать `SevenZipFolderDecoder`;
- сопоставить распакованные потоки с файлами;
- применить метаданные;
- подготовить результат для API декодирования или распаковки.

## `SevenZipFolderDecoder`

`SevenZipFolderDecoder` — центральная точка декодирования цепочек coder-ов внутри folder.

Он отвечает за:

- проверку topology folder-а;
- выбор packed stream;
- декодирование одиночных coder-сценариев;
- декодирование линейных цепочек;
- обработку BCJ2;
- проверку размеров;
- возврат согласованных результатов `Ok` / `InvalidData` / `NotSupported`.

Поддерживаемые ветки на текущем этапе:

- `Copy`;
- `LZMA`;
- `LZMA2`;
- `Delta`;
- `Swap2`;
- `Swap4`;
- BCJ-фильтры;
- `BCJ2`;
- `BZip2`;
- `PPMd`;
- `Deflate`;
- `Deflate64`;
- `AES` для поддерживаемых сценариев чтения 7z;
- экспериментальный `GOST` decoder-only path для поддержанных private method id.

Новые изменения в этом компоненте должны сопровождаться тестом, если они меняют публичный контракт, error-path или поведение на реальном архиве.

## Безопасность распаковки

Распаковка на диск считается отдельной зоной риска.

Перед записью файлов проект должен валидировать:

- абсолютные пути;
- относительные пути с выходом за целевую директорию;
- недопустимые символы;
- зарезервированные имена Windows;
- конфликт файлов и директорий;
- дублирующиеся пути;
- коллизии по регистру;
- недопустимые времена файлов;
- сценарии, которые могут привести к записи вне целевой директории.

Главное правило: архив не должен иметь возможности записать данные туда, куда пользователь явно не разрешал.

## Временные внешние зависимости

На этапе 1 допускаются узкие управляемые зависимости для отдельных codec-веток, если это помогает маленькими проверяемыми шагами закрыть реальные 7z-сценарии.

Сейчас к таким зависимостям относятся:

- `SharpZipLib` для `BZip2`;
- `SharpCompress` для отдельных методов, например `PPMd` и `Deflate64`.

Это временное архитектурное решение.

Долгосрочная цель — постепенно заменить такие зависимости собственными управляемыми реализациями проекта.

В первую очередь это касается:

- `PPMd`;
- `BZip2`;
- `Deflate`;
- `Deflate64`;
- возможных ZIP-совместимых сценариев.

При замене реализации внешний контракт `SevenZipFolderDecoder` должен сохраняться. Существующие тесты должны продолжать проходить.

## Writer-path 7z

На этапе 2 начат минимальный writer-path для 7z.

Writer развивается отдельно от уже стабилизированного decoder-path и не должен переписывать существующую логику чтения и декодирования.

Основной публичный вход:

- `SevenZipArchiveWriter.BuildArchive(...)`.

Входная модель:

- `SevenZipArchiveWriterEntry`.

`SevenZipArchiveWriterEntry` сейчас содержит:

- имя элемента;
- содержимое;
- признак директории.

Результат операции:

- `SevenZipArchiveWriteResult`.

Сейчас writer поддерживает минимальные сценарии:

- пустой архив;
- архив с одним пустым файлом;
- архив с несколькими пустыми файлами;
- архив с одной пустой директорией;
- архив со смесью пустых файлов и пустых директорий;
- архив с одним непустым файлом через `Copy`;
- архив с несколькими непустыми файлами через `Copy`;
- архив со смесью empty entries и непустых файлов через `Copy`.

Промежуточный итог flat writer-а: writer поддерживает простые валидные entry без вложенных путей.

Поддержанные типы entry:

- пустой файл;
- пустая директория;
- непустой файл через `Copy`.

Маршрутизация writer-а после входной validation:

- пустой набор entry строится как пустой архив;
- набор entry без файловых данных строится через empty-entry path;
- набор entry с непустыми файлами строится через `Copy` path;
- некорректные входные данные возвращают `InvalidData`.

Для `Copy` path packed data, `PackInfo` и `UnpackInfo` формируются только для непустых файлов.

`FilesInfo` всегда описывает полный набор entry.

Для одного непустого файла через `Copy` writer формирует:

- packed data между signature header и next header;
- `SignatureHeader`;
- `NextHeader`;
- `MainStreamsInfo`;
- `PackInfo`;
- `UnpackInfo`;
- `FilesInfo`;
- `Copy` coder;
- CRC packed stream-а;
- CRC folder stream-а;
- CRC файла.

Для нескольких непустых файлов через `Copy` writer формирует:

- packed data как конкатенацию содержимого файлов;
- `SignatureHeader`;
- `NextHeader`;
- `MainStreamsInfo`;
- `PackInfo` с несколькими packed stream-ами;
- `UnpackInfo` с несколькими folder-ами;
- отдельный `Copy` coder для каждого folder-а;
- `FilesInfo` со списком имён файлов;
- CRC для каждого packed stream-а;
- CRC для каждого folder stream-а;
- CRC для каждого файла.

Для смешанного сценария с empty entries и непустыми файлами через `Copy` writer формирует:

- packed data как конкатенацию содержимого только непустых файлов;
- `SignatureHeader`;
- `NextHeader`;
- `MainStreamsInfo`;
- `PackInfo` только для непустых файлов;
- `UnpackInfo` только для непустых файлов;
- отдельный `Copy` coder для каждого непустого файла;
- `FilesInfo` для всех entry;
- `EmptyStream` bit-vector для всех entry;
- `EmptyFile` sub-vector только для empty stream entry;
- `FilesInfo.Crc` с defined bit-vector;
- CRC только для непустых файлов.

Для mixed-сценария:

- пустой файл получает `EmptyStream = true` и `EmptyFile = true`;
- пустая директория получает `EmptyStream = true` и `EmptyFile = false`;
- непустой файл получает `EmptyStream = false`;
- CRC файла задаётся только для непустых файлов.

Для пустых файлов и пустых директорий writer формирует:

- `SignatureHeader`;
- `NextHeader`;
- `FilesInfo`;
- `EmptyStream`;
- `EmptyFile`;
- список имён файлов и директорий.

Packed data, `MainStreamsInfo`, `PackInfo` и `UnpackInfo` для этого сценария не формируются, потому что файловые данные отсутствуют.

Для пустого файла writer пишет:

- `EmptyStream = true`;
- `EmptyFile = true`.

Для пустой директории writer пишет:

- `EmptyStream = true`;
- `EmptyFile = false`.

Packed data, `MainStreamsInfo`, `PackInfo` и `UnpackInfo` для этого сценария не формируются, потому что файловые данные отсутствуют.

Существующий decoder-path используется как проверка результата writer-а:

- через `SevenZipArchiveReader`;
- через `SevenZipArchiveDecoder`;
- через round-trip тесты.

Writer-path пока не поддерживает:

- вложенные пути и файлы внутри директорий;
- timestamps;
- file attributes;
- solid-группировку;
- LZMA writer;
- LZMA2 writer;
- AES writer;
- GOST writer;
- encrypted header writer;
- streaming writer API.

Директория с данными считается некорректным входом writer-а и возвращает `InvalidData`.

## Контракт ошибок writer-а

Writer использует явный результат операции через `SevenZipArchiveWriteResult`.

Текущий контракт:

- `Ok` — архив успешно построен;
- `InvalidData` — некорректные входные данные: `null`, некорректное имя entry, директория с данными, дублирующееся имя или конфликт имён;
- `NotSupported` — сценарий распознан, но пока не входит в поддержанный writer-path;
- `InternalError` — неожиданное внутреннее состояние writer-а.

Writer не должен молча создавать частично некорректный архив.

## Контракт имён writer entry

Writer сейчас поддерживает только простые имена entry без вложенных путей.

Имя entry должно быть:

- непустым;
- не состоять только из пробельных символов;
- не содержать `\0`;
- не содержать `/` или `\`;
- не содержать недопустимые Windows-символы: `<`, `>`, `:`, `"`, `|`, `?`, `*`;
- не содержать управляющие символы `0x00..0x1F`;
- не быть зарезервированным Windows-именем;
- не заканчиваться точкой;
- не заканчиваться пробельным символом.

Writer также отклоняет:

- точные дубли имён;
- имена, отличающиеся только регистром;
- конфликт файла и директории с одинаковым именем;
- конфликт файла и директории с именами, отличающимися только регистром.

Зарезервированные Windows-имена отклоняются без учёта регистра:

- `CON`;
- `PRN`;
- `AUX`;
- `NUL`;
- `COM1` … `COM9`;
- `LPT1` … `LPT9`.

Имена с расширением тоже считаются зарезервированными, например `con.txt`, `COM1.log`, `lpt9.tmp`.

Похожие, но не зарезервированные имена разрешены, например `COM10.txt`, `LPT10.txt`, `CONSOLE.txt`, `auxiliary.txt`.

Точка и пробел внутри имени разрешены и сохраняются как часть имени entry.

Имена с завершающей точкой или завершающим пробельным символом отклоняются, потому что такие имена опасны для Windows-путей и могут привести к неоднозначному результату при распаковке.

Такие ошибки возвращают `InvalidData`.

Writer не должен создавать архивы, которые могут привести к конфликтам при безопасной распаковке на case-insensitive файловых системах.

## AES и зашифрованные архивы

AES не входил в этап 1 и вынесен в отдельный этап 1.5.

На этапе 1.5 реализован decoder-path для поддерживаемых AES-сценариев 7z.

Архитектурно AES добавлен как слой перед обычным декодированием packed stream-ов:

1. определяется AES coder;
2. разбираются свойства AES coder-а;
3. пароль передаётся через явный `SevenZipDecodeOptions`;
4. парольный материал кодируется как UTF-16LE без BOM;
5. выполняется key derivation по правилам 7zAES;
6. строится полный IV из AES properties;
7. packed stream расшифровывается через AES-256-CBC;
8. расшифрованные данные передаются в обычный pipeline `SevenZipFolderDecoder`.

Поддержаны два основных уровня AES:

- encrypted packed streams;
- encrypted header.

AES подключён в такие уровни:

- `SevenZipAesCoder`;
- `SevenZipAesProperties`;
- `SevenZipPassword`;
- `SevenZipAesKeyDerivation`;
- `SevenZipAesInitializationVector`;
- `SevenZipAesDecryptor`;
- `SevenZipAesPackedStreamDecryptor`;
- `SevenZipDecodeOptions`;
- `SevenZipFolderDecoder`;
- `SevenZipEncodedHeaderDecoder`;
- `SevenZipArchiveReader`;
- `SevenZipArchiveDecoder`.

На уровне верхнего API пароль проходит по цепочке:

```text
SevenZipArchiveDecoder
  -> SevenZipArchiveReader
  -> SevenZipEncodedHeaderDecoder
  -> SevenZipFolderDecoder
  -> AES decrypt
```

и по цепочке:

```text
ExtractToDirectory
  -> DecodeToEntries
    -> DecodeToArray
      -> SevenZipFolderDecoder
        -> AES decrypt
```

Покрытые real-archive сценарии:

- mhe=off, single-file, AES + Copy;
- mhe=off, single-file, AES + LZMA2;
- mhe=off, multi-file, AES + LZMA2;
- mhe=off, solid multi-file, AES + LZMA2;
- mhe=on, single-file, AES + LZMA2;
- mhe=on, multi-file, AES + LZMA2;
- mhe=on, solid multi-file, AES + LZMA2.

Ошибки AES должны возвращаться согласованно:

- без пароля — NotSupported;
- неверный пароль — InvalidData;
- повреждённые encrypted данные — InvalidData;
- неподдерживаемый AES-сценарий — NotSupported.

Для ExtractToDirectory важное правило остаётся прежним: ошибка AES не должна создавать файлы или директории на диске.

Запись AES-архивов не входит в текущую реализацию AES decoder-path. Она относится к будущему развитию writer-а.

## Экспериментальная GOST-ветка

GOST-поддержка является экспериментальным decoder-only расширением LzmaSharp.

Она подключена в decode-path 7z через `SevenZipFolderDecoder` и используется только для чтения архивов с private method id проекта.

Поддержанный сценарий:

- Kuznyechik;
- CTR;
- IV;
- direct-key KDF;
- расшифровка packed stream-ов;
- поддержка encrypted header.

Не входит в текущую архитектуру:

- запись GOST-архивов;
- совместимость со стандартным 7-Zip;
- Magma decrypt;
- полноценный KDF через Стрибог;
- streaming decrypt API.

## API-направление

Текущий фокус API:

- работа с `byte[]`, `ReadOnlySpan<byte>` и `Span<byte>` внутри ядра;
- декодирование архива в память;
- распаковка на диск через безопасный high-level API;
- передача пароля для AES через `SevenZipDecodeOptions`;
- явные результаты вместо неявных исключений для ожидаемых ошибок данных.

Долгосрочное направление:

- stream-friendly API там, где это действительно улучшает сценарии использования;
- меньше лишних копирований;
- более аккуратное управление буферами;
- возможность использовать ядро как библиотеку без привязки к UI.

## Энкодер

В проекте уже есть задел под энкодер, но он не является production-целью этапа 1.

Энкодер относится к этапу 2.

Для него архитектурно важны:

- независимость от текущих тестовых helper-ов;
- совместимость с эталонными реализациями;
- roundtrip-тесты;
- возможность записи 7z-контейнера;
- сохранение читаемости кода до начала оптимизации.

## Оптимизация

Оптимизация не является целью этапа 1.

Порядок работы фиксированный:

1. корректность;
2. тесты;
3. профилирование;
4. точечная оптимизация.

Допустимые направления будущей оптимизации:

- уменьшение аллокаций;
- пуллинг буферов;
- улучшение data-flow;
- `Span` / `Memory` там, где это измеримо полезно;
- stream-friendly pipeline;
- SIMD / intrinsics только после профилирования.

Низкоуровневая оптимизация не должна ухудшать читаемость публичной логики без измеримой причины.

## Правило изменения архитектуры

Любое существенное изменение архитектуры должно отвечать на вопросы:

- какой сценарий оно улучшает;
- какой риск оно закрывает;
- какие тесты подтверждают поведение;
- не ухудшает ли оно безопасность распаковки;
- не смешивает ли оно уровни ответственности.

Маленькие проверяемые изменения предпочтительнее больших переписываний.
