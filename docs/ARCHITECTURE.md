# Архитектура

## Цель

Понятное управляемое ядро на C# для LZMA / LZMA2 / 7z с упором на корректность и с запасом для последующей оптимизации по результатам профилирования.

## Текущая верхнеуровневая структура

### `Lzma.Core`

Основная библиотека.

Подразделы:

- `Checksums`
- `Lzma1`
- `Lzma2`
- `SevenZip`

### `Lzma.Core.Tests`

Проект тестов на `xUnit`.

Основные группы:

- `Checksums`
- `Lzma1`
- `Lzma2`
- `SevenZip`

### `vendor/lzma-sdk`

Эталонные исходники, которые используются для сверки поведения и анализа пограничных случаев.

## Принципы проектирования

- Основная логика остаётся в управляемом C#.
- Приоритет — читаемость и тестопригодность.
- Маленькие изолированные шаги предпочтительнее больших переписываний.
- Публичное поведение нужно закреплять тестами до начала оптимизаций.

## Основное направление API

Практический фокус на текущем этапе:

- работа с `byte[]`, `ReadOnlySpan<byte>` и `Span<byte>` в ядре;
- декодирование на уровне архива в память;
- распаковка на диск через явную валидацию путей;
- инкрементальное декодирование там, где оно уже помогает корректности и потоковым сценариям.

Долгосрочное направление:

- сохранять stream-friendly API там, где это реально улучшает использование;
- уменьшать лишние копирования после того, как функциональная корректность будет закрыта.

## Архитектура 7z на текущем этапе

Текущий путь декодирования концептуально делится на такие уровни:

1. разбор signature header;
2. определение и чтение next header;
3. разбор `StreamsInfo` и `FilesInfo`;
4. декодирование encoded header, когда это требуется;
5. декодирование на уровне folder;
6. восстановление архива в набор декодированных записей и файлов;
7. валидированная распаковка на диск.

## Модель безопасности распаковки

Распаковка — это не только «декодировать байты».

Перед записью на диск проект валидирует выходные пути и отклоняет небезопасные записи архива и конфликтующие варианты структуры вывода.

Это часть этапа 1, а не дополнительная опция.

## Текущие ограничения, которые важно явно фиксировать

Некоторые ветки кода осознанно уже, чем целевая итоговая реализация.

Примеры:

- AES не входит в этап 1.
- Поддержка encoded header сейчас ограничена более простыми поддержанными топологиями, которые уже реализованы в коде.
- Код, связанный с энкодером, уже существует, но пока не является основной production-целью проекта.

## Политика оптимизаций

Оптимизация — отдельный этап.

Порядок фиксированный:

1. корректность;
2. тесты;
3. профилирование;
4. точечная оптимизация.

Ни одна низкоуровневая хитрость не должна попадать в проект только потому, что «выглядит быстрой».
