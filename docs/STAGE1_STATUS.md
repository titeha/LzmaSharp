# Состояние этапа 1

## Критерий завершения этапа 1

Этап 1 считается завершённым, когда репозиторий явно демонстрирует надёжный управляемый декодер / распаковщик 7z для поддерживаемого подмножества формата.

Это означает, что:

- разбор архива работает для поддерживаемого подмножества;
- декодирование работает для поддерживаемого подмножества;
- безопасность распаковки покрыта тестами;
- для важных поддерживаемых сценариев есть тесты на реальных архивах;
- документация отражает реальное состояние проекта;
- сценарии, связанные с AES, явно остаются вне области этапа 1.

## Что уже есть

### Основные компоненты

- `SevenZipArchiveReader`;
- `SevenZipArchiveDecoder`;
- `SevenZipEncodedHeaderDecoder`;
- `SevenZipFolderDecoder`;
- вспомогательные части распаковки и модели декодированных файлов.

### Тестовая база

Уже есть большая зона тестов `SevenZip` с покрытием как синтетическими, так и реальными архивами.

### Семейства поддерживаемых методов, которые уже присутствуют в коде

- `Copy`;
- `LZMA`;
- `LZMA2`;
- `Delta`;
- `Swap2`;
- `Swap4`;
- BCJ-фильтры: `x86`, `ARM`, `ARMT`, `ARM64`, `PPC`, `SPARC`, `IA64`;
- `BCJ2`;
- `BZip2`;
- `PPMd`;
- `Deflate`;
- `Deflate64`.

### Работа по безопасности и устойчивости, которая уже видна в тестах

- небезопасные пути;
- дублирующиеся пути вывода;
- зарезервированные имена Windows;
- недопустимые символы пути;
- коллизии по регистру;
- некорректные времена файлов;
- сценарии, связанные с CRC;
- пустые потоки и подпотоки.

## Что явно не входит в этап 1

- AES-шифрованные архивы;
- зашифрованные заголовки;
- production-ready энкодер;
- переписывания ради оптимизации в первую очередь;
- приложение / UI.

## Какой дрейф документации нужно было устранить

До этого обновления документация репозитория уже не совпадала с реальностью в нескольких местах:

- старые названия структуры репозитория;
- старое обозначение тестового фреймворка;
- устаревшее описание плана тестирования;
- слишком узкое описание этапа 1 как шага только про декодер `LZMA2`.

## Рекомендуемый порядок дальнейшей работы

1. Завершить точечную сверку покрытия `SevenZipFolderDecoder`.
2. Не добавлять новые синтетические тесты без явной причины:
   - безопасность распаковки;
   - crash / exception path;
   - публичный контракт `Ok` / `InvalidData` / `NotSupported`;
   - ветка, которую реально можно сломать при оптимизации.
3. Почистить устаревшие имена тестов и комментарии.
4. Прогнать полный набор тестов.
5. Объявлять этап 1 завершённым только тогда, когда сам репозиторий делает этот вывод очевидным.

### Текущее состояние покрытия SevenZipFolderDecoder

`SevenZipFolderDecoder` покрыт прямыми тестами по основным поддерживаемым веткам:

- одиночные coder-сценарии: `Copy`, `LZMA`, `LZMA2`, `Delta`, `Swap2`, `Swap4`, BCJ-фильтры, `BZip2`, `PPMd`, `Deflate`, `Deflate64`;
- BCJ2:
  - подготовка входных потоков;
  - выбор финального выхода;
  - merge через `TryDecodeBcj2ToArray`;
  - topology / size-limit / malformed-stream проверки;
- линейная topology folder-а;
- выбор `pack stream` для одного и нескольких folder-ов;
- проверки `PackInfo`, `UnpackInfo`, `FolderUnpackSizes`, `PackSizes`, `PackPos`;
- negative-path для недопустимых свойств coder-ов и неконсистентных размеров.

Дальше новые тесты для `SevenZipFolderDecoder` добавляются только при обнаружении конкретного незакрытого риска, а не ради полного перебора всех синтетических комбинаций.
