# Дорожная карта архиватора

## Назначение документа

Этот документ описывает путь от текущего управляемого декодера / распаковщика к полноценному архиватору.

Основной общий `ROADMAP.md` остаётся главным планом проекта. Этот файл фиксирует именно прикладную линию развития архиватора: writer, CLI, собственные codec-реализации, оптимизация и UI.

## Текущее состояние

## Текущий статус

Этапы 1, 1.5 и 1.6 завершены.

Проект перешёл от decoder-only стабилизации к подготовке этапа 2: encoder / writer.

Этот документ описывает направление работ по writer-части и не должен восприниматься как описание текущего decoder-path.

Уже закрыто:

- базовое чтение и распаковка поддерживаемых 7z-архивов;
- AES decoder-path;
- экспериментальный GOST Kuznyechik CTR direct-key decoder-path.

В фокусе следующего основного этапа:

- LZMA encoder;
- LZMA2 encoder;
- базовый 7z writer;
- round-trip тестирование.

Не входит в базовый объём writer-этапа:

- AES writer;
- GOST writer;
- Magma;
- полноценный GOST KDF через Стрибог;
- расширенные криптографические сценарии.

## Блок 1: базовый декодер 7z

Статус: финальная часть этапа 1.

Цель блока — иметь надёжную основу для чтения архивов.

Сюда относятся:

- `SevenZipArchiveReader`;
- `SevenZipArchiveDecoder`;
- `SevenZipEncodedHeaderDecoder`;
- `SevenZipFolderDecoder`;
- безопасная распаковка;
- тесты реальных архивов;
- документация текущих ограничений.

AES и зашифрованные заголовки не входят в этот блок.

## Блок 1.5: AES для 7z

Статус: будущий отдельный блок после закрытия этапа 1.

Цель блока — добавить поддержку зашифрованных 7z-архивов поверх уже стабилизированного декодера.

Ориентировочный состав:

- распознавание AES coder-а;
- разбор свойств AES coder-а;
- API для передачи пароля;
- derivation ключа по правилам 7z AES;
- расшифровка packed stream-ов;
- поддержка зашифрованных заголовков, если она понадобится для реальных архивов;
- тесты на корректный пароль;
- тесты на отсутствующий пароль;
- тесты на неверный пароль;
- тесты на повреждённые данные;
- проверка, что ошибки AES не приводят к небезопасной записи на диск.

Запись AES-архивов относится к будущему развитию writer-а и не является обязательной частью этого блока.

## Блок 2: writer / encoder

Статус: будущий этап 2.

Цель блока — реализовать запись архивов, а не только чтение.

Основные направления:

- усилить собственный LZMA encoder;
- усилить собственный LZMA2 encoder;
- реализовать запись структуры 7z;
- записывать `StreamsInfo`;
- записывать `FilesInfo`;
- записывать CRC и метаданные;
- поддержать single-file и multi-file сценарии;
- поддержать empty file и empty directory;
- подготовить основу для solid-сценариев.

Минимальные проверки writer-а:

- roundtrip внутри проекта;
- наше кодирование -> декодирование эталонной реализацией;
- эталонное кодирование -> декодирование нашей реализацией;
- сравнение структуры записанных архивов с ожидаемой;
- тесты на реальные файлы и директории.

## Блок 3: собственные codec-реализации

Статус: будущий блок после функциональной стабилизации.

На этапе 1 допускаются временные управляемые зависимости для отдельных методов 7z.

Долгосрочная цель — постепенно убрать сторонние библиотеки из критичных codec-веток.

В первую очередь это касается:

- `PPMd`;
- `BZip2`;
- `Deflate`;
- `Deflate64`;
- возможных ZIP-совместимых сценариев.

Правило замены:

- внешний контракт `SevenZipFolderDecoder` должен сохраняться;
- существующие тесты должны продолжать проходить;
- новая реализация добавляется маленькими проверяемыми шагами;
- сначала корректность, потом производительность.

## Блок 4: CLI

Статус: будущий прикладной слой.

CLI нужен для удобной работы с реальными данными и ручной проверки поведения.

Ориентировочные команды:

```text
lzma-sharp list <archive>
lzma-sharp unpack <archive> <directory>
lzma-sharp pack <directory> <archive>
```

Возможные дополнительные команды:

```text
lzma-sharp test <archive>
lzma-sharp info <archive>
```

CLI не должен содержать основную бизнес-логику архивации. Он должен использовать публичный API ядра.

## Блок 5: benchmark и оптимизация

Статус: будущий этап после функциональной стабилизации.

Оптимизация начинается только после тестов и профилирования.

Инструменты:

- BenchmarkDotNet;
- dotnet-trace;
- PerfView;
- профилировщики памяти.

Направления:

- уменьшение аллокаций;
- `ArrayPool`;
- улучшение потоковой обработки;
- оптимизация hot path;
- SIMD / intrinsics только после подтверждения профилированием;
- многопоточный pipeline для больших данных.

## Блок 6: UI и сервисные сценарии

Статус: поздний этап.

Возможные направления:

- desktop UI;
- простое приложение для упаковки и распаковки;
- сервисные сценарии;
- интеграция с другими приложениями;
- расширение платформенной поддержки.

UI не должен появляться раньше стабильного ядра, иначе он начнёт маскировать проблемы архитектуры и API.

## Правила развития архиватора

- Сначала корректность и безопасность.
- Затем тесты на реальные данные.
- Затем writer.
- Затем собственные codec-реализации.
- Затем оптимизация.
- Затем прикладные оболочки.

Большие переписывания нежелательны. Предпочтительны маленькие изменения с понятным тестовым подтверждением.
