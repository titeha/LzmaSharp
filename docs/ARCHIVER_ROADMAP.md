# Дорожная карта архиватора

## Назначение документа

Этот документ описывает путь от управляемого декодера / распаковщика к полноценному архиватору.

Основной общий `ROADMAP.md` остаётся главным планом проекта.

Этот файл фиксирует прикладную линию развития архиватора:

- writer;
- encoder;
- CLI;
- собственные codec-реализации;
- оптимизация;
- UI.

## Текущее состояние

Этапы 1, 1.5 и 1.6 завершены.

Этап 2 начат.

Проект перешёл от decoder-only стабилизации к постепенному развитию encoder / writer-направления.

Уже закрыто:

- базовое чтение и распаковка поддерживаемых 7z-архивов;
- AES decoder-path;
- экспериментальный GOST Kuznyechik CTR direct-key decoder-path.

На старте этапа 2 уже реализованы первые минимальные writer-сценарии:

- основной вход `SevenZipArchiveWriter.BuildArchive(...)`;
- входная модель `SevenZipArchiveWriterEntry`;
- результат операции `SevenZipArchiveWriteResult`;
- пустой архив;
- архив с одним пустым файлом;
- архив с несколькими пустыми файлами;
- архив с одной пустой директорией;
- архив со смесью пустых файлов и пустых директорий;
- архив с одним непустым файлом через `Copy`;
- архив с несколькими непустыми файлами через `Copy`;
- архив со смесью empty entries и непустых файлов через `Copy`;
- вложенный пустой файл;
- вложенный непустой файл через `Copy`;
- явная пустая директория и файл внутри неё;
- сохранение вложенных `/`-paths в `FilesInfo.Names`.

Для `Copy`-сценария writer формирует:

- packed data;
- `SignatureHeader`;
- `NextHeader`;
- `MainStreamsInfo`;
- `PackInfo`;
- `UnpackInfo`;
- `FilesInfo`;
- `Copy` coder;
- CRC packed stream-а;
- CRC folder stream-а;
- CRC файла.

Для нескольких непустых файлов через `Copy` writer формирует несколько packed stream-ов, несколько folder-ов, отдельный `Copy` coder для каждого folder-а и CRC для каждого packed stream-а, folder stream-а и файла.

Для mixed Copy-сценария writer поддерживает архивы, где empty entries и непустые `Copy`-файлы находятся в одном `FilesInfo`.

Packed data, `PackInfo` и `UnpackInfo` формируются только для непустых файлов.

`FilesInfo` описывает все entry и содержит `EmptyStream`, `EmptyFile` и `Crc` с defined bit-vector.

Для пустых файлов и пустых директорий writer формирует только header-структуру:

- `SignatureHeader`;
- `NextHeader`;
- `FilesInfo`;
- `EmptyStream`;
- `EmptyFile`;
- список имён файлов и директорий.

Packed data, `MainStreamsInfo`, `PackInfo` и `UnpackInfo` для этого сценария не формируются.

Покрыто:

- round-trip тестами через существующий decoder-path;
- round-trip тестами для empty-entry, multi-Copy и mixed Copy-сценариев;
- структурными тестами через `SevenZipArchiveReader`;
- проверкой `PackInfo`, `UnpackInfo`, `FilesInfo` и `Copy` coder-а;
- проверкой `EmptyStream`, `EmptyFile` и `FilesInfo.Crc` bit-vector-ов;
- negative-тестами для повреждённых данных и CRC;
- explicit `InvalidData` для некорректных входных данных.

Промежуточный итог flat writer-а:

- writer поддерживает простые валидные entry, включая безопасные вложенные `/`-paths;
- пустые файлы и пустые директории пишутся через empty-entry path;
- непустые файлы пишутся через `Copy` path;
- mixed Copy-сценарии поддерживают empty entries и непустые `Copy`-файлы в одном архиве;
- `FilesInfo` описывает полный набор entry;
- packed data, `PackInfo` и `UnpackInfo` формируются только для непустых файлов.

Вложенность задаётся через `/` внутри имени entry.

Writer уже пишет базовые Windows attributes:

- `Archive = 0x20` для файлов;
- `Directory = 0x10` для директорий;
- attributes пишутся через `FilesInfo.WinAttrib`;
- `AllAreDefined = true`;
- `External = false`.

Writer отклоняет небезопасные path-сценарии:

- absolute path;
- path с завершающим `/`;
- path с пустыми сегментами;
- path с `.` или `..` сегментами;
- path с `\`;
- path с некорректным сегментом;
- parent-file conflict;
- path, отличающиеся только регистром.

Проверка parent-entry выполняется без учёта регистра.

Parent-directory другого регистра разрешает вложенный entry.

Parent-file другого регистра возвращает `InvalidData`.

Полные вложенные path, отличающиеся только регистром, также возвращают `InvalidData`.

Не входит в базовый объём writer-этапа:

- AES writer;
- GOST writer;
- Magma;
- полноценный GOST KDF через Стрибог;
- расширенные криптографические сценарии;
- CLI;
- UI;
- тяжёлая оптимизация.

## Блок 1: базовый decoder-path 7z

Статус: завершён.

Цель блока — иметь надёжную основу для чтения и распаковки архивов.

Сюда относятся:

- `SevenZipArchiveReader`;
- `SevenZipArchiveDecoder`;
- `SevenZipEncodedHeaderDecoder`;
- `SevenZipFolderDecoder`;
- безопасная распаковка;
- тесты реальных архивов;
- документация текущих ограничений.

AES и зашифрованные заголовки не входили в этап 1 и были вынесены в этап 1.5.

## Блок 1.5: AES decoder-path для 7z

Статус: завершён.

Цель блока — добавить поддержку зашифрованных 7z-архивов поверх уже стабилизированного decoder-path.

Реализовано:

- распознавание AES coder-а;
- разбор свойств AES coder-а;
- API для передачи пароля;
- derivation ключа по правилам 7zAES;
- расшифровка packed stream-ов;
- поддержка зашифрованных заголовков;
- real-archive тесты;
- negative-тесты на отсутствующий пароль, неверный пароль и повреждённые данные;
- проверка, что ошибки AES не приводят к небезопасной записи на диск.

Запись AES-архивов относится к будущему развитию writer-а и не входит в базовый объём этапа 2.

## Блок 1.6: экспериментальный GOST decoder-path

Статус: завершён.

Цель блока — добавить экспериментальный decoder-only путь для GOST-сценариев LzmaSharp.

Реализовано:

- private method id для экспериментальных GOST coder-ов;
- Kuznyechik;
- CTR;
- IV;
- direct-key KDF;
- расшифровка packed stream-ов;
- поддержка encrypted header;
- archive-level интеграция;
- synthetic-тесты.

Не входит:

- Magma decrypt;
- полноценный KDF через Стрибог;
- совместимость со стандартным 7-Zip;
- GOST writer.

Magma, Стрибог/KDF и остальные GOST-сценарии остаются поздним направлением после завершения основных этапов проекта.

## Блок 2: writer / encoder

Статус: в работе.

Цель блока — постепенно реализовать запись архивов, а не только чтение.

Первый writer-сценарий уже реализован через `Copy`.

Дальнейшие направления:

- постепенно расширять `SevenZipArchiveWriter.BuildArchive(...)`;
- поддержать произвольные file attributes через публичную модель writer-а;
- поддержать timestamp-метаданные;
- развивать запись структуры 7z;
- развивать `StreamsInfo`;
- развивать `FilesInfo`;
- развивать CRC и метаданные;
- подготовить основу для solid-сценариев;
- усилить собственный LZMA encoder;
- усилить собственный LZMA2 encoder.

Минимальные проверки writer-а:

- round-trip внутри проекта;
- сравнение структуры записанных архивов с ожидаемой;
- проверка через `SevenZipArchiveReader`;
- проверка через `SevenZipArchiveDecoder`;
- тесты на реальные файлы и директории по мере появления соответствующих сценариев;
- совместимость с эталонными инструментами там, где это применимо.

На этапе 2 не нужно заранее добавлять synthetic edge-case тесты без реализуемого writer-сценария.

## Блок 3: собственные codec-реализации

Статус: будущий блок после функциональной стабилизации.

На ранних decoder-этапах допускаются временные управляемые зависимости для отдельных методов 7z.

Долгосрочная цель — постепенно убрать сторонние библиотеки из критичных codec-веток.

В первую очередь это касается:

- `PPMd`;
- `BZip2`;
- `Deflate`;
- `Deflate64`;
- возможных ZIP-совместимых сценариев.

Правило замены:

- внешний контракт `SevenZipFolderDecoder` должен сохраняться;
- существующие тесты должны продолжать проходить;
- новая реализация добавляется маленькими проверяемыми шагами;
- сначала корректность, потом производительность.

## Блок 4: CLI

Статус: будущий прикладной слой.

CLI нужен для удобной работы с реальными данными и ручной проверки поведения.

Ориентировочные команды:

```text
lzma-sharp list
lzma-sharp unpack
lzma-sharp pack
```

Возможные дополнительные команды:

```text
lzma-sharp test
lzma-sharp info
```

Статус: будущий этап после функциональной стабилизации.

## Блок 6: UI и сервисные сценарии

Статус: поздний этап.

Возможные направления:

desktop UI;
простое приложение для упаковки и распаковки;
сервисные сценарии;
интеграция с другими приложениями;
расширение платформенной поддержки.

UI не должен появляться раньше стабильного ядра, иначе он начнёт маскировать проблемы архитектуры и API.

## Правила развития архиватора

Сначала корректность и безопасность.
Затем тесты на реальные данные.
Затем постепенное расширение writer-а.
Затем собственные codec-реализации.
Затем оптимизация.
Затем прикладные оболочки.

Большие переписывания нежелательны.

Предпочтительны маленькие изменения с понятным тестовым подтверждением.
