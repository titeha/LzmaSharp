# Минималистичный стиль C# для LzmaSharp

Эти правила обязательны для любых изменений C# в проекте.

## Основной принцип

- Делай минимальное корректное изменение.
- Не добавляй код, типы, абстракции, зависимости, проверки или комментарии «на будущее».
- Не рефактори соседний код без прямого требования задачи.
- Не меняй поведение ради сокращения кода.
- При конфликте с `.editorconfig`, анализаторами или существующим устойчивым стилем остановись и сообщи о конфликте.

## `using` и пространства имён

Перед добавлением `using` проверь:

1. существующие `global using`;
2. `GlobalUsings.cs`;
3. `ImplicitUsings` в проекте;
4. уже подключённые пространства имён;
5. наличие алиаса или конфликта имён.

Правила:

- Не добавляй неиспользуемые, дублирующие или уже глобально подключённые `using`.
- После правки удали созданные тобой неиспользуемые `using`.
- Не добавляй `using` только потому, что он обычно встречается в похожем коде.
- Не сортируй и не переформатируй несвязанные `using`.

## NuGet-пакеты и зависимости

- Не добавляй `PackageReference`, если задача явно этого не требует.
- Сначала проверь, решается ли задача средствами BCL, существующей зависимостью, `ProjectReference`, общей конфигурацией или централизованным управлением пакетами.
- Перед добавлением пакета проверь `Directory.Packages.props`, `Directory.Build.props`, все релевантные `.csproj` и существующие транзитивные зависимости.
- Не добавляй пакет ради одного простого helper-а или API, имеющегося в .NET.
- Не удаляй пакет в обычной задаче стиля.
- Удаление пакетов выполняется только отдельной задачей с доказательством, что пакет не используется как библиотека, analyzer, source generator, build target, runtime/reflection dependency или тестовый эталон.

## Фигурные скобки

Для `if`, `else`, `for`, `foreach`, `while`, `using` и `lock`:

- Не используй фигурные скобки, если тело состоит ровно из одного простого оператора.
- Сохраняй скобки, если тело многострочное, содержит комментарий или директиву, вложенное управление потоком либо без скобок возникает неоднозначность или ухудшается читаемость.
- Не меняй скобки в несвязанных участках файла.
- Не удаляй скобки, если это запрещено действующим `.editorconfig` или analyzer-правилом; вместо этого сообщи о конфликте.

Пример:

```csharp
if (value < 0)
    throw new ArgumentOutOfRangeException(nameof(value));
```

Не делай:

```csharp
if (value < 0)
{
    throw new ArgumentOutOfRangeException(nameof(value));
}
```

## Приведения и выражения

- Не добавляй явное приведение типа, если неявное преобразование уже корректно и однозначно.
- Сохраняй приведение только когда оно требуется компилятором, выбором overload, числовой семантикой, `checked`/`unchecked`, enum, interop или предотвращением потери данных.
- Не добавляй лишние скобки вокруг выражений.
- Не вводи временную переменную, используемую один раз, если она не улучшает смысл, не предотвращает повторное вычисление и не нужна для `ref`, `out` или отладки.
- Предпочитай прямой `return` промежуточной переменной без смысловой нагрузки.
- Не создавай private helper для одного тривиального вызова.
- Не дублируй одинаковые сообщения и константы без реальной необходимости общего контракта.
- Не добавляй `async`/`await` и не удаляй их только ради краткости, если это меняет исключения, отмену, стек или момент выполнения.

## Комментарии и документация

- Не добавляй комментарии, пересказывающие очевидный код.
- Комментарий должен объяснять причину, инвариант, формат или неочевидное ограничение.
- Не создавай XML-документацию для test-only helper-а, если проект этого не требует.
- Комментарии, XML-документация и сообщения коммитов — на русском языке.

## Контроль размера изменения

- Одна задача — одна причина изменения.
- Не смешивай очистку стиля с исправлением поведения.
- Не меняй более трёх файлов в одной задаче очистки без отдельного согласования.
- Не выполняй массовое форматирование.
- Не запускай `dotnet format` с записью по всему репозиторию без прямого разрешения.

## Проверка перед завершением

Обязательно:

1. `git diff --check`;
2. `git diff --name-only`;
3. сборка затронутого проекта;
4. целевые тесты;
5. проверка, что не добавлены лишние `using`, пакеты, приведения, переменные, helper-методы и комментарии;
6. подтверждение отсутствия несвязанных изменений.

Не заявляй об успехе без фактически выполненной проверки.
